# 修改方案：显式 Region 搬运模型

## 最终结论

目标模型改为：

```text
应用层负责语义：
  选择哪个 expert / KV block 要卸载或恢复
  维护 expert -> envelope_region_ids
  维护 KV block 生命周期和 block -> VA range 映射
  判断 hot/cold/active/evictable

内核层只负责搬运：
  注册 region_id -> base/length
  维护 region_id -> state
  对应用层点名的 region_id 或 VA range 执行 release / restore / prefetch
  根据 state 做幂等跳过
```

因此，内核层不再理解 MoE / KV 的业务语义。内核 region 不需要保存：

```text
pool
layer_id
expert_id
role
evictable
active
MOE_EXPERT_WEIGHT / EXPERT_ENVELOPE 等语义 flags
```

这些判断都在应用层完成。内核只需要知道“这个 ID 对应哪段 VA，现在是什么状态，是否需要搬运”。

如果旧 ioctl ABI 暂时仍包含这些字段，可以在过渡期继续传 0 或兼容值，但内核新路径不得依赖它们。最终应新增或收敛到最小 region 注册 / 搬运接口。

## 最小内核模型

内核每个 region 只保留：

```text
KernelRegion
  region_id
  base
  length
  state = GPU | CPU | PREFETCHING_GPU | PREFETCHING_CPU | UNKNOWN
```

必须保留：

- `region_id`：应用层点名要操作的对象。
- `base/length`：内核执行迁移、unmap、prefetch 所需的 VA range。
- `state`：用于幂等判断和失败恢复。

不再保留：

- `pool=WEIGHT/KV`
- `layer_id/expert_id`
- `role=W13/W2/KV_BLOCK`
- `flags=EVICTABLE/PROTECTED/EXPERT_ENVELOPE/...`

内核操作必须是幂等的：

```text
release(region):
  state == CPU              -> skip success
  state == GPU              -> release, success 后 state=CPU
  state == PREFETCHING_GPU  -> 等待或转 release，成功后 state=CPU
  state == UNKNOWN          -> 返回需要上层处理，不盲目成功

restore(region):
  state == GPU              -> skip success
  state == CPU              -> restore/prefetch, success 后 state=GPU
  state == PREFETCHING_CPU  -> 等待或转 restore，成功后 state=GPU
  state == UNKNOWN          -> 返回需要上层处理，不盲目成功
```

如果去掉语义字段，以下内核功能也必须移到应用层或删除：

```text
按 pool 自动挑 victim
按 evictable/protected flags 判断能否驱逐
按 role 判断是不是 MoE expert
按 expert_id/layer_id 做 reserved-slot owner 统计
按 pool 做内核侧 budget/reclaim 策略
fault 路径按 pool/role 做业务分类
```

新模型中，内核只执行应用层明确指定的 region/range。

## Expert 最小模型

### 应用层保留

应用层只保留 expert 到 envelope 的归属关系：

```text
ExpertRecord
  layer_id
  global_expert_id
  aggregate_state = GPU | CPU | UNKNOWN
  envelope_region_ids = [region_id, ...]
```

示例：

```text
ExpertRecord(layer_id=7, global_expert_id=1)
  aggregate_state = GPU
  envelope_region_ids = [
    "weights:7:1:envelope:1000000000:80000",
    "weights:7:1:envelope:1000080000:80000",
    "weights:7:1:envelope:1000200000:80000",
    "weights:7:1:envelope:1000280000:80000",
  ]
```

这里 `layer_id/global_expert_id` 只存在于应用层的 ExpertRecord 中，不再复制到每个 envelope，也不下沉到内核。

应用层 envelope 不再保存：

```text
pool
layer_id
global_expert_id
local_expert_id
role / envelope_role
state
evictable
active
driver_flags
stage
source
logical_region_id
logical_ptr
logical_bytes
driver_cpu_offloaded_reserved_registered
driver_registered / driver_register_status 的重复副本
```

注册时应用层临时从 `w13_weight`、`w2_weight` 计算 envelope 覆盖范围。计算完成后只保存 envelope ID 集合。

### 内核层保留

对上面的 expert，内核只看到 4 个普通 region：

```text
KernelRegion
  region_id = "weights:7:1:envelope:1000000000:80000"
  base      = 0x1000000000
  length    = 0x80000
  state     = GPU
```

内核不知道这个 region 属于 layer 7、expert 1，也不知道它来自 `w13` 还是 `w2`。这些都已经由应用层在选择 `envelope_region_ids` 前完成。

### Expert 卸载流程

```text
应用层：
  1. 策略选中 ExpertRecord(7, 1)
  2. 读取 envelope_region_ids
  3. 调用 driver_release_regions(envelope_region_ids)

内核：
  1. 对每个 region_id 查 base/length/state
  2. state==CPU 则跳过
  3. state==GPU/PREFETCHING_GPU 则执行 release/unmap
  4. 成功后更新该 region state=CPU
  5. 失败则返回失败项或 state=UNKNOWN

应用层：
  全部成功 -> ExpertRecord.aggregate_state=CPU
  部分失败 -> ExpertRecord.aggregate_state=UNKNOWN
```

### Expert 重新搬运流程

```text
应用层：
  1. 即将使用 ExpertRecord(7, 1)
  2. 读取 envelope_region_ids
  3. 调用 driver_restore_regions(envelope_region_ids)

内核：
  1. state==GPU 则跳过
  2. state==CPU/PREFETCHING_CPU 则 restore/prefetch
  3. 成功后 state=GPU
  4. 失败则返回失败项或 state=UNKNOWN

应用层：
  全部成功 -> ExpertRecord.aggregate_state=GPU
  部分失败 -> ExpertRecord.aggregate_state=UNKNOWN
```

该流程不需要内核理解 expert 语义。

## Expert 正确性约束

应用层必须保证：

1. `expert -> envelope_region_ids` 完整。
2. 一个 envelope 只能属于一个 expert。
3. hot/cold/active/evictable 判断在调用内核前完成。
4. 所有 envelope 成功后才更新 expert 聚合状态。
5. 任何 envelope 失败都不能把 expert 标为成功卸载或成功恢复。

尤其是 envelope 独占性必须在编译阶段检查：

```text
如果 512 KiB envelope 同时覆盖 expert 1 和 expert 2：
  禁止注册为单 expert envelope
  或缩小粒度 / 调整分配布局
```

否则卸载 expert 1 会误影响 expert 2。

## KV 最小模型

KV 在当前方案中只走原生 / 批量 `prefetch + advise` 路径，不走自定义 `driver_release(region_id)`。因此 KV physical span 不再注册到内核 region 表，只保留在应用层，用于把 logical block ids 翻译成 VA ranges。

KV 仍保留两类应用层对象：

```text
PhysicalKVSpan:
  负责 block id -> VA range

LogicalKVBlock:
  负责 scheduler/block 生命周期状态
```

二者不是包含关系，而是通过同一个 block_id 坐标系在迁移时临时对应。当前阶段不做 group 级精细迁移：输入仍是 block_ids，应用层对所有相关 PhysicalKVSpan 生成 ranges，并对所有 group 的同名 block 回写状态。

### PhysicalKVSpan

应用层用于 block id 到 VA range 的转换：

```text
PhysicalKVSpan
  span_id / region_id   # 应用层 identity，不是 kernel region
  ptr
  size_bytes
  page_size
  max_block_id
```

示例：

```text
PhysicalKVSpan
  span_id      = "kv_phys:0:model.layers.7.self_attn:0"
  ptr          = 0x3000000000
  size_bytes   = 8 MiB
  page_size    = 256 KiB
  max_block_id = 31
```

这些字段只在应用层保存。内核不需要知道：

```text
group_id
layer_name
tensor_index
page_size
max_block_id
block_id
```

其中 `group_id/layer_name/tensor_index` 可以继续用于生成 `span_id`，但生成后不需要重复塞进 metadata，也不参与当前迁移策略判断。

```text
当前不做 group 精细迁移：
  collect_uvm_kv_cache_physical_ranges_for_blocks(block_ids)
  -> 遍历所有 PhysicalKVSpan
  -> 对每个 span 计算这些 block_ids 对应的 VA ranges
  -> 迁移完成后回写所有 group 的 LogicalKVBlock.state

暂不新增：
  collect_uvm_kv_cache_physical_ranges_for_blocks(group_id, block_ids)
  kv_group:<group_id>:<block_id> 级别的独立物理迁移策略
```

### LogicalKVBlock

应用层 scheduler 维护逻辑 block 状态：

```text
LogicalKVBlock
  group_id
  block_id
  state = GPU | CPU | PREFETCHING_GPU | PREFETCHING_CPU | UNKNOWN
  lifecycle_state  # 仅 dynamic pool 仍需要时保留
  ref_cnt          # 仅 dynamic pool 仍需要时保留
```

LogicalKVBlock 不进入内核，不注册 driver region。

不再保留生产路径 metadata：

```text
stage
source
metadata_only
block_hash
in_free_queue
offload_capable
ever_used
bytes_per_block  # 如果 region.bytes 或配置已有
```

### KV 物理迁移流程

如果要卸载 block 4 到 block 7：

```text
应用层：
  1. 找到 PhysicalKVSpan
  2. range_ptr   = span.ptr + 4 * span.page_size
  3. range_bytes = (7 - 4 + 1) * span.page_size
  4. 调用 batch_offload_ranges_to_cpu_with_executor([(range_ptr, range_bytes)])

CUDA/UVM：
  1. cudaMemAdviseSetPreferredLocation(range, CPU)
  2. cudaMemPrefetchAsync(range, CPU)
  3. 不需要 kernel region_id

应用层：
  1. 成功后更新 kv:0:4 ... kv:0:7 的 LogicalKVBlock.state=CPU
  2. 失败则保持或标记 UNKNOWN
```

恢复到 GPU 时同理，应用层根据 block ids 重新计算 VA ranges，然后调用 `batch_prefetch_ranges_to_device_with_executor(ranges, device)`。因此 KV 的语义、地址映射和 block 状态都在应用层；内核 region 表不保存 KV physical / logical 信息。

## 要删除的 MoE 冗余字段和逻辑

删除或迁移以下 MoE envelope metadata：

```text
envelope_role
envelope_global_expert_id
envelope_local_expert_id
logical_region_id
logical_ptr
logical_bytes
envelope_base
envelope_bytes
envelope_granularity_bytes
envelope_policy
stage
source
expert_envelope
driver_tag_skip
driver_tag_skip_reason
driver_cpu_offloaded_reserved_registered
driver_registered / driver_register_status 的重复 metadata 副本
```

删除或改造以下逻辑：

```text
_uvm_weight_expert_role_states
VLLM_UVM_*_TARGET_ROLES
_uvm_expert_weight_region_id(..., role)
_uvm_stage_m_expert_weight_slices() 的 role 输出
按 role 判断完整性的检查
内核中 role == W13 || role == W2 的判断
内核中 pool/flags/expert_id/layer_id 参与策略判断的路径
```

`w13_weight` 和 `w2_weight` 只允许作为 envelope 编译阶段的临时输入，不允许作为运行时策略语义。

## 要删除的 KV 冗余字段和调试路径

### KV physical registration

生产路径只保留：

```text
region_id
ptr
size_bytes
page_size
max_block_id
```

删除：

```text
phase
source
total_blocks
allocation_blocks
dtype
shape
stride
device
skipped_non_tensor
skipped_non_cuda
skipped_noncontiguous
skipped_invalid
```

### register_uvm_kv_cache_physical_ranges()

该函数当前同时写：

```text
_KV_PHYSICAL_RANGE_RECORDS
UvmPoolResidencyManager / driver region
```

新方案中：

```text
_KV_PHYSICAL_RANGE_RECORDS:
  保存最小 PhysicalKVSpan，用于 block -> VA range

UvmPoolResidencyManager / driver region:
  KV prefetch-only 路径不再注册
  删除 register_uvm_residency_region(pool="kv", region_id="kv_phys:...", driver_register=True)
  删除 get_uvm_residency_region_snapshot("kv_phys:...") 去重判断
```

删除 KV physical residency metadata：

```text
stage
source
group_id
layer_name
tensor_index
page_size
total_blocks
max_block_id
block_addressable
metadata_only
```

只有在未来重新引入以下能力时，才需要恢复 KV 内核注册：

```text
自定义 driver release / restore by region_id
内核按 KV pool 做 budget / reclaim
内核按 KV region 统计 residency
内核 fault 路径需要识别地址属于 KV
内核维护 KV region state
```

### KV result/log 调试代码

删除生产路径中的：

```text
_register_uvm_kv_cache_physical_ranges():
  skipped_* 计数
  result.update(...)
  logger.info("Registered UVM KV physical ranges ...")

initialize_kv_cache_tensors():
  kv_physical_result 变量
  打印 result=%s 的 debug warning

register_uvm_kv_cache_physical_ranges():
  clear_existing in returned result
  skipped reason counters

collect_uvm_kv_cache_physical_ranges_for_blocks():
  range_records
  block_intervals
  requested_block_count
  range_count
  range_bytes
```

生产路径只需要：

```text
collect_uvm_kv_cache_physical_ranges_for_blocks(block_ids) -> ranges
batch_offload_ranges_to_cpu_with_executor(ranges, ...)
batch_prefetch_ranges_to_device_with_executor(ranges, ...)
```

所有额外 counters 和 records 只能在显式 debug flag 下生成。

## Address-map 诊断删除

`_record_uvm_moe_address_map()` 可以删除。它不是注册、卸载、恢复或 fault 处理的一部分，只在 `VLLM_UVM_MOE_ADDRESS_MAP_ENABLE=1` 时扫描 tensor 并写 JSONL。

删除范围：

```text
FusedMoE.__init__:
  uvm_moe_address_map_enabled
  uvm_moe_address_map_file
  uvm_moe_address_map_driver_probe

FusedMoE helpers:
  _append_uvm_moe_address_map()
  _uvm_tensor_address_record()
  _record_uvm_moe_address_map()

Call sites:
  select_experts_after_topk
  stage_m_init_offload_begin
```

保留 `probe_driver_capable_range()`，因为真实注册路径仍可能用它校验可注册地址。

## 实施阶段

### Phase 1：应用层 expert 原子化

- 新建 `ExpertRecord(layer_id, global_expert_id)`。
- 编译 `expert -> envelope_region_ids`。
- 校验 envelope 独占性。
- `run_uvm_init_weight_offload()` 改为按 expert 生成 work item。
- 不再按 role 生成两个逻辑 region。

### Phase 2：内核最小 region 注册

新增或收敛注册接口为：

```text
register_region(region_id, base, length)
```

内核只写：

```text
region_id -> base/length/state
```

旧 ABI 中的 `pool/layer_id/expert_id/role/flags` 在新路径中不参与判断。

### Phase 3：显式搬运 API

新增或收敛执行接口为：

```text
release_regions(region_ids)
restore_regions(region_ids)
offload_ranges(ranges)
prefetch_ranges(ranges)
query_region_states(region_ids)
```

这些 API 只基于 region id 或 VA range 执行，不做业务选择。

### Phase 4：删除内核语义策略

删除或禁用：

```text
pool-based victim selection
role-based expert detection
flag-based expert envelope detection
kernel-side weight/KV budget reclaim policy
kernel-side expert owner accounting
```

这些策略全部回到应用层。

### Phase 5：KV metadata 收敛

- `_KV_PHYSICAL_RANGE_RECORDS` 改成最小 PhysicalKVSpan。
- LogicalKVBlock 只保留 group/block/state 和必要生命周期字段。
- KV physical span 不再注册到 UvmPoolResidencyManager / driver region；prefetch-only 路径直接使用 VA ranges。
- 暂不实现 group 级精细迁移；仍按 block_ids 对所有相关 PhysicalKVSpan 生成 ranges。
- 删除 KV 注册统计、shape/device dump、range_records 等调试字段。

### Phase 6：清理兼容代码

- 删除 role 相关环境变量和 target-role 逻辑。
- 删除 W13/W2 driver constants 的使用。
- 删除 envelope metadata 宽字段。
- 删除 MoE address-map 诊断。
- 删除旧 ioctl ABI 中不再使用字段，或保留为兼容但内核忽略。

## 验收条件

必须满足：

1. 同一 cold expert 编译出的 envelope 覆盖字节数与旧实现一致。
2. 一个 envelope 不会被两个 expert 共享。
3. 卸载 expert 时，应用层只提交该 expert 的 envelope IDs。
4. 所有 envelope release 成功后，expert 聚合状态才变为 CPU。
5. 任一 envelope 失败时，expert 聚合状态为 UNKNOWN。
6. 恢复 expert 时，应用层只提交该 expert 的 envelope IDs。
7. 内核 state 能正确跳过重复 release / restore。
8. KV 同一组 block ids 在删减前后生成相同的 `(ptr, bytes)` ranges。
9. KV prefetch-only 路径不再产生 `kv_phys:...` kernel region 注册。
10. 内核不再依赖 pool/layer/expert/role/flags 判断是否搬运。
11. 所有调试字段删除后，吞吐实验和功能测试仍能完成卸载与重新搬运。

## 推荐落地边界

这个方案不再追求“内核也理解 UVM 对象语义”。最终边界是：

```text
应用层：语义、策略、对象归属、调度状态
内核层：region/range 搬运、状态幂等、失败返回
```

只要应用层完整维护 `expert -> envelope_region_ids` 和 KV block 到 VA range 的映射，内核层不保存 MoE/KV 语义信息也能保证卸载和重新搬运。

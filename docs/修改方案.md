# 修改方案：精简 `run_uvm_init_time_weight_placement()`

## 一、结论

当前函数的总体流程是正确的：先完成所有 Cold Expert 的注册和 release，再把剩余 Hot Expert 的全部 envelope 合并成一个批次 prefetch 到 GPU，最后同步并提交状态。

可以删除大量纯诊断、重复协议校验和兼容分支，但不能删除 placement 的事务边界。精简后的核心流程应收敛为：

```text
执行 matched CPU offload
  -> 检查功能开关和幂等状态
  -> 对所有 MoE 模块完成 Cold Expert release
  -> 收集 Hot Expert envelope region IDs
  -> 一次批量 GPU prefetch
  -> 一次 CUDA synchronize
  -> 提交 Region 和 Expert 的 GPU 状态
  -> 失败时统一降级为 UNKNOWN 并终止启动
```

本方案只描述后续代码修改，不表示运行时代码已经完成修改。

## 三、可以删除的内容

### 1. 时间、数量和日志记录

删除：

```python
started = time.monotonic()
matched_issued = ...
issued_modules = 0
issued_modules += 1
```

以及函数末尾的三组 `logger.info()`。这些数据不参与 Expert 选择、release、prefetch、同步或状态提交。

`_run_uvm_matched_cpu_offload_manifest()` 的调用仍需保留，只是不再保存其计数返回值：

```python
self._run_uvm_matched_cpu_offload_manifest()
```

异常会继续向上抛出，因此 `except` 中仅用于重复打印堆栈的 `logger.warning(..., exc_info=True)` 也可以删除。

### 2. 重复的模块协议检查

仓库中目前只有 `FusedMoE` 实现以下三个入口：

```text
run_uvm_init_weight_offload
get_uvm_init_hot_expert_region_ids
set_uvm_init_hot_expert_state
```

遍历整个模型时，仍需要用 `run_uvm_init_weight_offload` 判断一个模块是否为目标 MoE 模块；一旦模块被选中，另外两个方法应视为同一内部协议的一部分，不必再次执行 `getattr + callable` 检查。

因此保留一次模块筛选：

```python
init_offload = getattr(module, "run_uvm_init_weight_offload", None)
if not callable(init_offload):
    continue
```

删除对 `collect_hot` 和 `mark_hot` 的重复动态校验。为避免未来新增模块只实现半套协议，应在类型测试或模块构造测试中验证协议完整性，而不是每次初始化 placement 时重复检查。

### 3. executor 集合和一致性检查

删除：

```python
hot_executors: set[str] = set()
hot_executors.add(...)
if len(hot_executors) != 1:
    raise RuntimeError(...)
```

`uvm_weight_executor` 当前由同一进程环境配置，每个 `FusedMoE` 模块应得到相同值。精简实现可直接使用第一个 Hot 模块的 executor：

```python
executor=hot_modules[0].uvm_weight_executor
```

更彻底的后续方案是把 executor 提升为 `GPUModelRunner` 的单一配置字段，在 runner 构造时初始化一次。不能在尚未新增该字段前直接假设 `self.uvm_weight_executor` 已存在。

### 4. CUDA 可用性检查

删除：

```python
if not torch.cuda.is_available():
    raise RuntimeError(...)
```

该函数属于 `GPUModelRunner` 的 post-warmup 路径；能够执行到这里本身就要求 CUDA worker 已初始化。若 CUDA 环境损坏，`current_device()`、prefetch 或 synchronize 会直接失败并进入统一回滚，无需提前做一次重复探测。

### 5. 外层 region ID 去重

删除：

```python
hot_region_ids = list(dict.fromkeys(hot_region_ids))
```

`prepare_uvm_regions_for_gpu_placement()` 内部已经对输入 ID 去重；同时 Expert envelope 编译阶段应保证 ownership 唯一。外层再次去重不影响正确性，只是重复工作。

### 6. all-cold/legacy 额外同步分支

删除没有 Hot region 时的兼容同步：

```python
elif self._env_flag_enabled("VLLM_UVM_INIT_WEIGHT_SYNC", default=True):
    torch.cuda.synchronize()
```

Cold Expert 使用显式 driver release。底层 ioctl 返回成功时，release/remote-read setup 已完成；它不依赖此处额外 CUDA 同步。Hot 批次存在时仍必须保留唯一一次 synchronize。

删除该分支后，`VLLM_UVM_INIT_WEIGHT_SYNC` 不再参与此函数；若仓库中没有其他消费者，应继续删除对应配置和测试。

### 7. 应用层中间态写入

可以删除对每个 Hot 模块的：

```python
module.set_uvm_init_hot_expert_state("prefetching_gpu")
```

`prepare_uvm_regions_for_gpu_placement()` 已把每个实际 Region 设置为 `PREFETCHING_GPU`。初始化期间尚未进入 serving，没有并发消费者需要读取 Expert 的聚合中间态。因此应用层 ExpertRecord 只需在最终成功时写 `GPU`，失败时写 `UNKNOWN`。

这里删除的是重复的 Expert 聚合中间态，不是底层 Region 的 `PREFETCHING_GPU` 状态机。

### 8. 冗长注释和错误详情

将解释 cold-before-hot、单同步点的长注释收敛为一两行。错误只需指出失败阶段，不必把包含统计和地址信息的整个结果字典拼进异常：

```python
raise RuntimeError("Hot Expert prefetch failed")
raise RuntimeError("Hot Expert placement commit failed")
```

## 四、必须保留的正确性逻辑

以下内容不是调试代码，不能删除。

### 1. 功能开关

```python
VLLM_UVM_INIT_WEIGHT_OFFLOAD_ENABLE
```

它决定是否启用显式 Expert 注册与初始放置，不能让未启用该机制的模型进入 release/prefetch 路径。

### 2. 幂等保护

重复执行会再次 release、prefetch 和提交同一批 Region，因此 `_uvm_init_weight_placement_done` 必须保留。

建议在 `GPUModelRunner.__init__` 中明确初始化：

```python
self._uvm_init_weight_placement_done = False
```

之后主函数可使用直接字段访问，删除 `getattr(..., False)` 这种防御式写法。

### 3. 两阶段顺序

必须先让所有模块完成 Cold release，再收集并 prefetch Hot envelope：

```text
release layer 0 cold
release layer 1 cold
...
collect all hot regions
one hot prefetch batch
```

不能在遍历每一层时交替执行 `release -> hot prefetch`。否则后续层的 release 和 HBM 压力可能立即挤出前一层刚搬回的 Hot 页。

### 4. prepare 返回值检查

`prepare_uvm_regions_for_gpu_placement()` 可能因为 Region 未注册、range 无效、driver 状态更新失败或部分 prefetch 失败而返回 `ok=False`。不检查就继续同步和提交，会把未完整驻留的 Hot Expert 错记为 GPU。

### 5. CUDA synchronize

prefetch 是异步提交。只有 synchronize 成功，才能证明该批次在当前同步点已经完成。删除同步会让 `GPU` 仅表示“命令已提交”，而不是“迁移已完成”。

### 6. commit 返回值检查

`commit_uvm_regions_gpu_placement(..., synchronized=True)` 同时验证 Region 是否仍处于可提交状态，并把 Region 状态改为 `GPU`。若 driver state update 失败，Expert 不能继续标记为 GPU。

### 7. 失败回滚和继续抛错

任一阶段异常时必须：

```text
把可能处于 PREFETCHING_GPU 的 Region 降级为 UNKNOWN
把相关 Hot Expert 聚合状态降级为 UNKNOWN
保持 done=False
重新抛出异常，禁止 worker 带错误状态进入 serving
```

`commit_uvm_regions_gpu_placement(..., synchronized=False)` 不是日志操作；它是同步失败后的 Region 状态回滚。

## 五、推荐的精简实现

在 `GPUModelRunner.__init__` 中先初始化：

```python
self._uvm_init_weight_placement_done = False
```

主函数可收敛为：

```python
def run_uvm_init_time_weight_placement(self) -> None:
    self._run_uvm_matched_cpu_offload_manifest()

    if not self._env_flag_enabled(
        "VLLM_UVM_INIT_WEIGHT_OFFLOAD_ENABLE",
        default=False,
    ):
        return
    if self._uvm_init_weight_placement_done:
        return

    expert_modules = []
    hot_modules = []
    hot_region_ids = []

    try:
        # 所有 Cold release 完成后再统一放置 Hot Expert。
        with uvm_enabled_allocation_phase("enabled:init_weight_offload"):
            for module in self.get_model().modules():
                init_offload = getattr(
                    module,
                    "run_uvm_init_weight_offload",
                    None,
                )
                if not callable(init_offload):
                    continue
                init_offload()
                expert_modules.append(module)

            for module in expert_modules:
                region_ids = module.get_uvm_init_hot_expert_region_ids()
                if region_ids:
                    hot_modules.append(module)
                    hot_region_ids.extend(region_ids)

        if hot_region_ids:
            device = int(torch.cuda.current_device())
            result = prepare_uvm_regions_for_gpu_placement(
                hot_region_ids,
                device=device,
                executor=hot_modules[0].uvm_weight_executor,
            )
            if not result["ok"]:
                raise RuntimeError("Hot Expert prefetch failed")

            torch.cuda.synchronize(device)
            result = commit_uvm_regions_gpu_placement(
                hot_region_ids,
                synchronized=True,
            )
            if not result["ok"]:
                raise RuntimeError("Hot Expert placement commit failed")

            for module in hot_modules:
                module.set_uvm_init_hot_expert_state("gpu")

        self._uvm_init_weight_placement_done = True

    except Exception:
        if hot_region_ids:
            commit_uvm_regions_gpu_placement(
                hot_region_ids,
                synchronized=False,
            )
        for module in hot_modules:
            module.set_uvm_init_hot_expert_state("unknown")
        self._uvm_init_weight_placement_done = False
        raise
```

与当前实现相比，该版本删除了计时、计数、完成日志、异常重复日志、executor 集合、CUDA 预检查、重复 region 去重、重复方法校验、all-cold 同步和应用层 `PREFETCHING_GPU` 写入，同时保留完整的 placement 正确性。

## 六、进一步收敛的可选项

如果希望继续缩短主函数，可以定义内部 `UvmExpertPlacementModule` 协议，并提供 `_iter_uvm_expert_modules()`。该 helper 只负责从混合模型模块中筛出完整实现协议的 MoE 模块，不保存统计信息。

也可以让 `prepare_uvm_regions_for_gpu_placement()` 和 `commit_uvm_regions_gpu_placement()` 在失败时直接抛异常，而不是返回包含大量诊断字段的字典。届时主函数可删除两处显式 `ok` 判断，但迁移函数内部仍必须检查完整成功，不能通过忽略返回值来达到表面精简。

不建议在本次修改中同时改变这两个公共函数的返回契约，以免扩大调用者和测试的修改范围。

## 十三、重新检查发现的剩余问题

以下内容不改变当前主路径的结论，但说明仓库中仍保留旧注册、旧策略、重复状态模型和调试设施。最终清理完成前，不能把“默认未启用”表述成“代码已不存在”。

### 1. allocator 仍保留可选 KV 自动注册

C++ allocator 仍解析 `VLLM_UVM_DRIVER_KV_TAG_ENABLE`，默认值为 `false`，见 [allocator 配置](D:/github/uvm/workloads/vllm/vllm/uvm_test/uvm_allocator.cpp:4566)。当人为开启该开关且 allocation phase 为 KV cache 时，allocator 会把整次 managed allocation 注册为 driver Region，见 [allocator KV tag](D:/github/uvm/workloads/vllm/vllm/uvm_test/uvm_allocator.cpp:6301)。

因此当前准确状态是：

```text
默认 Python KV 主路径：
  PhysicalKVSpan 仅保存在应用层
  通过 VA range 执行 prefetch
  不注册内核 Region

人为打开 VLLM_UVM_DRIVER_KV_TAG_ENABLE：
  allocator 按整次 allocation 注册内核 Region
  注册粒度不是 LogicalKVBlock，也不是应用层 PhysicalKVSpan
```

如果最终设计明确规定“KV 只允许应用层按 VA range 搬运，禁止任何 KV kernel registration”，应物理删除：

```text
driver_kv_tag_enable 全局配置
VLLM_UVM_DRIVER_KV_TAG_ENABLE 环境变量解析
KV allocation phase 自动识别和注册分支
driver_kv_tag_allocs / driver_kv_tag_failures 计数
仅为该分支存在的日志、统计和 unregister 路径
相关配置文档与测试
```

验收时应在整个仓库搜索 `VLLM_UVM_DRIVER_KV_TAG_ENABLE` 和 `driver_kv_tag`，结果为零；创建 KV cache 后，driver Region 表中也不得出现 allocator-level KV allocation。

### 2. 旧 Phase-N pool/role/flags 策略仍留在内核源码

旧 pool budget、victim 选择、role/flags 分类和 reclaim 实现从 [uvm.c 的旧 Phase-N 代码](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:1011) 开始，主体位于 `#if 0` 中，不参与当前编译。旧 pool/reclaim ioctl 定义仍保留在 [uvm_ioctl.h](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_ioctl.h:1462)，但对应命令已不再路由。

这些代码可以物理删除，包括：

```text
pool budget 和动态 budget 结构
pool state/victim trace
pool reclaim 和 region reclaim 旧接口
active KV protection 旧接口
pool/role/semantic flags 分类
只服务于旧策略的统计、trace 和辅助函数
未路由的 ioctl 编号及参数结构
对应的 C/C++ wrapper、Python ctypes 和测试
```

但不能按 `PHASE_N` 名称整体删除。当前显式 Region 路径仍复用：

```text
UVM_PHASE_N_REGION_STATE_UNKNOWN
UVM_PHASE_N_REGION_STATE_CPU
UVM_PHASE_N_REGION_STATE_PREFETCHING_CPU
UVM_PHASE_N_REGION_STATE_GPU
UVM_PHASE_N_REGION_STATE_PREFETCHING_GPU
```

应先把这些枚举迁移或重命名为通用 `UVM_REGION_STATE_*`，同步修改 kernel、ioctl shim 和 Python 映射，再删除剩余 Phase-N 命名。验收标准是：内核仍能按 `region_id -> base/length/state` 完成 release/restore，但源码不再包含 pool、expert role、victim 或 budget 语义。

### 3. `ExplicitRegionRegistry.experts` 是未接入主路径的重复模型

[register_expert](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm_region.py:224) 和 [update_expert_state](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm_region.py:275) 目前只有单元测试调用，运行时没有调用者。真实 ExpertRecord 保存在每个 `FusedMoE._uvm_expert_records` 中，形成了两套潜在的 Expert 状态容器：

```text
真实运行时：
  FusedMoE._uvm_expert_records

未接入的通用模型：
  ExplicitRegionRegistry.experts
```

本方案选择删除通用 registry 中未使用的 Expert 层，而不是再引入一次状态同步。应删除：

```text
ExplicitRegionRegistry.experts
register_expert()
update_expert_state()
只验证这两个接口的测试
仅由这些接口使用的 aggregate-state 辅助代码（确认无其他调用后）
```

必须保留 `ExplicitRegionRegistry.regions` 及其 Region 注册、查询和状态更新能力，因为 Hot placement 和显式 release/restore 仍依赖 `region_id -> base/length/state`。

清理后的唯一关系是：

```text
FusedMoE ExpertRecord:
  (layer_id, expert_id) -> envelope_region_ids + aggregate_state

ExplicitRegionRegistry:
  region_id -> base + length + state
```

### 4. `UvmPoolResidencyManager` 已退化成兼容壳

[UvmPoolResidencyManager](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm_pool_residency.py:114) 仍暴露 pool budget、pool state 和 reclaim API，但当前行为是：

```text
driver pool budget：unsupported
driver reclaim：unsupported
regions_snapshot()：[]
真实显式 Region：由独立 ExplicitRegionRegistry 管理
```

它不再承担 Region ownership 或实际迁移控制，继续保留会让调用者误以为内核仍具有 pool 自治策略。建议分两步拆除：

第一步删除或改写所有调用方：

```text
不再通过 manager 注册/查询 Region
不再调用 set/sync driver pool budget
不再调用 driver pool reclaim/state snapshot
需要的最小 estimated-bytes 信息移到实际消费者本地
```

第二步删除兼容壳：

```text
UvmPoolResidencyManager
get_uvm_pool_residency_manager()
pool budget/reclaim 公共 wrapper
unsupported 状态码和 reason
空 regions_snapshot() 及相关测试
仅为旧 manager 存在的环境变量
```

删除前必须用仓库全局搜索确认没有调用者依赖 manager 的 estimated byte 统计。不能只删除类定义而留下公共 wrapper，也不能把 unsupported 返回静默改成成功。

### 5. 调试和统一快照记录仍未完全删除

KV policy 仍调用：

```text
record_unified_kv_target()
record_unified_residency_snapshot()
record_config()
```

入口见 [uvm_kv_runtime_policy.py](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/uvm_kv_runtime_policy.py:322)。`GPUModelRunner` 和 C++ allocator 也仍保留 address map、allocation phase、policy result、计数和耗时等调试记录。

这些记录不决定 Expert 选择、KV block 生命周期、VA range 计算、release、prefetch 或状态提交，可以继续删除。清理原则是：

```text
保留：
  影响分支决策的配置
  迁移结果 ok/reason
  correctness 所需的 Region/Expert/LogicalKVBlock 状态
  启动失败时必要的异常

删除：
  address dump/address map
  allocation trace
  policy snapshot 历史
  仅用于日志展示的计数和耗时
  debug result.update() 字段
  只服务于上述记录的环境变量、锁、容器和 import
```

删除记录函数时要同步修改调用点和测试，避免保留构造大型字典但不再输出的“半删除”状态。debug 开关开启或关闭也不得再改变迁移控制结果。

### 6. 剩余清理的建议顺序

```text
1. 删除 allocator KV tag，彻底禁止 KV kernel registration
2. 删除 ExplicitRegionRegistry.experts 重复模型
3. 迁移通用 Region state 枚举，物理删除旧 Phase-N pool/reclaim ABI 和源码
4. 移除 UvmPoolResidencyManager 的所有调用者，再删除兼容壳
5. 删除 KV、GPUModelRunner 和 allocator 的调试记录设施
6. 全仓搜索旧开关、旧 API 和旧字段，更新测试与文档
```

完成后的目标边界保持不变：

```text
Expert：
  应用层选择 Expert，并保存 Expert -> envelope_region_ids
  内核只按 region_id 执行 release/restore

KV：
  应用层保存 PhysicalKVSpan 和 LogicalKVBlock
  应用层计算 VA range，CUDA/UVM prefetch 执行搬运
  不向内核注册 KV Region

内核 Region：
  只保存 region_id/base/length/state
  不理解 pool/layer/expert/role/flags
```

## 十四、精简 `driver_release_regions()` 的 result 和 candidate

### 1. 结论

[driver_release_regions](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:1151) 当前把 ioctl 诊断信息、block/byte 统计、FD 探测信息和真正的控制结果全部放进 `result`、`candidate` 和 `entries`，字段明显过多。

对当前显式 Expert release 主路径，最终调用者真正需要回答的只有两个问题：

```text
1. 整个 region-id 批次是否全部成功？
2. 每个 region_id 分别是否成功？
```

FD 探测逻辑还需要一个仅在函数内部使用的问题：

```text
3. 当前 FD 上是否已经产生物理操作进度，因而不能换另一个 FD 重试？
```

因此建议将最终返回值收敛为：

```python
{
    "ok": bool,
    "statuses": dict[int, bool],
}
```

将内部 candidate 收敛为：

```python
{
    "statuses": dict[int, bool],
    "made_progress": bool,
}
```

`candidate["ok"]` 也不是必需字段，可以随时由所有请求 ID 的状态计算：

```python
complete = all(statuses.get(region_id, False) for region_id in normalized)
```

### 2. 最终 result 中可以删除的字段

当前 result 中以下字段不参与上层 Region 状态提交，可以删除：

```text
ioctl
entry_count
success_count
failure_count
skipped_blocks
attempted_blocks
success_blocks
failure_blocks
attempted_bytes
released_bytes
failed_bytes
remote_map_blocks
remote_map_failure_blocks
cpu_resident_bytes
remote_mapped_bytes
newly_remote_mapped_bytes
first_error
first_failed_region_id
first_failed_block
entries
attempted_fd_count
```

其中 `entry_count/success_count/failure_count` 都可从输入和 `statuses` 推导；错误码、首个失败位置、block/byte 计数及 FD 次数仅用于诊断。

不能只保留一个聚合 `ok`。一次批量 release 可能部分成功，上层 [release_uvm_regions](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm_pool_residency.py:312) 必须按 Region 分别提交：

```text
成功 Region -> CPU
失败 Region -> UNKNOWN
```

如果只返回 `ok=False`，上层无法知道哪些 Region 已经实际释放；如果把所有 Region 都写成 `UNKNOWN`，虽然保守，但会丢失幂等跳过依据，并可能触发不必要的重复操作。因此最小正确返回契约必须包含逐 Region `statuses`。

### 3. candidate 中可以删除的字段

当前 `_run_release_on_fd()` 的 candidate 重复保存了完整 result 的全部计数，还增加了：

```text
fd_source
entries
```

这些字段均不需要保留。内部 candidate 最小只需：

```python
statuses: dict[int, bool]
made_progress: bool
```

`made_progress` 必须保留，因为现有逻辑会依次尝试 inherited/existing UVM FD 和新建 FD。若某个 existing FD 已经释放了部分 VA block，再换 FD 重试整批 Region，可能造成重复执行或掩盖部分成功状态。

它不需要累计精确字节数，布尔值即可：

```python
made_progress |= (
    int(params.attempted_blocks) > 0
    or int(params.released_bytes) > 0
    or int(params.newly_remote_mapped_bytes) > 0
)
```

其中 `newly_remote_mapped_bytes` 对 `remote_read=True` 是必要补充：即使没有新增 release bytes，只要已经建立了新的 remote mapping，也不能把该次尝试当作“无操作”后换 FD 重试。

### 4. 哪些 ioctl 字段仍必须读取，但不再返回

删除 result/candidate 字段不等于删除 ioctl 参数结构中的所有输出。[_region_release_entry_to_dict](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:1064) 当前利用以下数据判断一次 Region 操作是否真正成功：

```text
ret
rmStatus
flags
length
first_error
block_count
attempted_blocks
skipped_blocks
released_bytes
remote_map_failure_blocks
cpu_resident_bytes
remote_mapped_bytes
newly_remote_mapped_bytes  # made_progress
```

普通 release 需要区分：

```text
有效幂等成功：Region 已在 CPU，ioctl 成功且没有错误
伪成功：ioctl 表面返回成功，但根本没有找到有效 VA block
```

remote-read 还必须验证：

```python
params.remote_map_failure_blocks == 0
params.cpu_resident_bytes >= params.length
params.remote_mapped_bytes >= params.length
```

否则可能把“页面已在 CPU、但 GPU 只读映射没有完整建立”误判为成功。

这些字段应只在 `_run_release_on_fd()` 内计算两个布尔结果：

```text
region_ok
region_made_progress
```

计算完成后立即丢弃，不再构造包含所有原始字段的 entry 字典。

### 5. 删除 `_region_release_entry_to_dict()` 的大字典

建议把 `_region_release_entry_to_dict()` 改为最小判定 helper，例如：

```python
def _region_release_outcome(
    params: _ExpertOffloadReleaseParams,
    *,
    ret: int,
) -> tuple[bool, bool]:
    raw_ok = ret == 0 and int(params.rmStatus) == 0
    remote_read = bool(
        int(params.flags) & UVM_EXPERT_OFFLOAD_RELEASE_FLAG_REMOTE_READ
    )

    activity = (
        int(params.block_count),
        int(params.attempted_blocks),
        int(params.success_blocks),
        int(params.failure_blocks),
        int(params.skipped_blocks),
        int(params.attempted_bytes),
        int(params.released_bytes),
        int(params.failed_bytes),
        int(params.remote_map_blocks),
        int(params.remote_map_failure_blocks),
        int(params.cpu_resident_bytes),
        int(params.remote_mapped_bytes),
        int(params.newly_remote_mapped_bytes),
    )
    idempotent = (
        raw_ok
        and not remote_read
        and int(params.length) > 0
        and int(params.first_error) == 0
        and not any(activity)
    )
    ok = raw_ok and (
        idempotent
        or int(params.block_count) > 0
        or int(params.attempted_blocks) > 0
        or int(params.skipped_blocks) > 0
        or int(params.released_bytes) > 0
    )
    if remote_read:
        ok = (
            ok
            and int(params.remote_map_failure_blocks) == 0
            and int(params.cpu_resident_bytes) >= int(params.length)
            and int(params.remote_mapped_bytes) >= int(params.length)
        )

    made_progress = (
        int(params.attempted_blocks) > 0
        or int(params.released_bytes) > 0
        or int(params.newly_remote_mapped_bytes) > 0
    )
    return ok, made_progress
```

这里的局部 `activity` 只参与幂等判定，不进入返回值。`saved_errno`、`reason`、`raw_ok`、`idempotent`、地址、长度及所有计数不再组成 Python 字典。

### 6. 精简后的 FD 执行流程

`_run_release_on_fd()` 可改为：

```python
def _run_release_on_fd(fd: int) -> tuple[dict[int, bool], bool]:
    statuses = {}
    made_progress = False

    for region_id in normalized:
        params = _ExpertOffloadReleaseParams()
        params.region_id = region_id
        params.gpu_uuid = gpu_uuid
        params.flags = flags

        ret = _libc_ioctl(
            fd,
            _UVM_EXPERT_OFFLOAD_RELEASE_IOCTL,
            params,
        )
        ok, progressed = _region_release_outcome(params, ret=int(ret))
        statuses[region_id] = ok
        made_progress |= progressed

    return statuses, made_progress
```

外层不再保存 `candidate_results`、比较 released bytes 或选择“统计上最佳”的 candidate：

```python
def _result(statuses: dict[int, bool]) -> dict[str, object]:
    return {
        "ok": all(statuses.get(region_id, False) for region_id in normalized),
        "statuses": statuses,
    }

for existing_fd in existing_fds:
    statuses, made_progress = _run_release_on_fd(existing_fd)
    if _result(statuses)["ok"] or made_progress:
        return _result(statuses)

statuses, _ = _run_release_on_fd(new_fd)
return _result(statuses)
```

existing FD 上既未成功也没有物理进度时才尝试下一个 FD；一旦全部成功或已有物理进度，立即返回当前逐 Region 状态。

异常或 GPU UUID 获取失败时返回：

```python
{
    "ok": False,
    "statuses": {region_id: False for region_id in normalized},
}
```

空输入保持幂等成功：

```python
{"ok": True, "statuses": {}}
```

### 7. 上层调用同步修改

`release_uvm_regions()` 当前解析 `result["entries"]`，需要改为直接使用：

```python
driver_statuses = result["statuses"]

for numeric_id, region in numeric_to_region.items():
    ok = bool(driver_statuses.get(numeric_id, False))
    region.state = RegionState.CPU if ok else RegionState.UNKNOWN
    statuses[region.region_id] = ok
```

不再使用：

```text
return_entries=True
entries
aggregate_ok 作为缺失 entry 的回退
```

缺少某个 Region 的 status 必须按失败处理，不能用批次 `ok` 替代，否则返回结构缺失时可能把未确认的 Region 错写为 CPU。

`return_entries` 参数也应从 `driver_release_regions()` 的签名和所有调用点删除。

### 8. 建议删除的诊断代码

如果项目按“只保留功能所需最小字段”执行，还可以删除：

```text
ctypes.set_errno(0) 和 ctypes.get_errno()  # errno 不再返回或记录时
fd_source 字符串构造
candidate_results 列表
best=max(...) 排序
attempted_fd_count
result/candidate 的重复预填充大字典
仅验证 reason、idempotent 和统计字段的测试断言
```

异常仍应通过 `ok=False + statuses=False` 反馈给上层；是否保留一条启动失败日志是可观测性选择，不影响控制正确性。

### 9. 测试和验收条件

需要更新 [release 结果测试](D:/github/uvm/workloads/vllm/vllm/tests/test_uvm_release_result.py:1) 和 [显式 Expert Region 测试](D:/github/uvm/workloads/vllm/vllm/tests/test_uvm_explicit_expert_regions.py:160)，至少覆盖：

```text
普通 release 的完整成功
普通 release 的有效 CPU 幂等成功
无有效 VA block 时失败
remote-read 映射完整时成功
remote-read 仅 CPU resident、映射不完整时失败
批次部分成功时返回准确的逐 Region statuses
existing FD 无进度失败时继续尝试其他 FD
existing FD 已产生部分进度时禁止整批换 FD 重试
UUID/打开 FD/ioctl 异常时所有请求 Region 返回失败
release_uvm_regions 按逐 Region status 提交 CPU 或 UNKNOWN
```

最终验收返回结构固定为：

```text
driver_release_regions:
  ok
  statuses

内部 FD candidate:
  statuses
  made_progress
```

不得再返回 block/byte 统计、FD 来源、首个错误、地址 geometry 或完整 ioctl entry。

## 十五、删除 Expert release 的 2 MiB strict 模式和 `max_blocks`

### 1. 结论

重新检查 Python、ioctl ABI 和内核实现后，可以确认：

```text
STRICT_2M_BLOCKS：
  当前应用层没有定义该常量
  当前应用层没有任何入口发送该 flag
  driver_release_regions() 固定使用 SUBCHUNK_64K
  可以删除

max_blocks：
  Python 参数默认值始终为 0
  所有运行时调用者都没有传入非零值
  当前功能要求一个 Expert 的指定 envelope 完整 release
  人为制造部分 release 不符合该语义
  可以删除
```

两项删除后，Expert release 的行为统一为：

```text
应用层明确提交 region_id 列表
  -> 每个 Region 扫描完整 VA 范围
  -> 按 64 KiB subchunk 完成 release
  -> remote_read 模式下继续建立并验证完整只读映射
  -> 任一范围不完整则该 Region 返回失败并置为 UNKNOWN
```

### 2. 删除 2 MiB strict 模式

旧 flag 定义位于 [uvm_ioctl.h](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_ioctl.h:1796)：

```c
UVM_EXPERT_OFFLOAD_RELEASE_FLAG_STRICT_2M_BLOCKS
```

内核仍保留三段相关逻辑：

```text
allowed-flags 掩码接受 STRICT_2M_BLOCKS
禁止 STRICT_2M_BLOCKS 与 SUBCHUNK_64K 同时出现
当 Region 不是完整 2 MiB VA block 时返回失败
```

入口分别见 [flag 校验](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:11297)、[互斥校验](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:11304) 和 [2 MiB 边界分支](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:11447)。

当前 Python 只定义：

```python
UVM_EXPERT_OFFLOAD_RELEASE_FLAG_SUBCHUNK_64K = 1 << 2
UVM_EXPERT_OFFLOAD_RELEASE_FLAG_REMOTE_READ = 1 << 3
```

并在 [driver_release_regions](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:1201) 中无条件设置 `SUBCHUNK_64K`。仓库中不存在发送 `STRICT_2M_BLOCKS` 的应用层代码，因此该模式已是不可达兼容代码。

应删除：

```text
UVM_EXPERT_OFFLOAD_RELEASE_FLAG_STRICT_2M_BLOCKS 宏
allowed-flags 掩码中的该位
STRICT_2M_BLOCKS 与 SUBCHUNK_64K 的互斥检查
非完整 2 MiB block 时失败的 strict 分支
对应注释、测试和文档
```

删除后不能改变 64 KiB 主路径：Region 仍必须满足 64 KiB 对齐，并继续调用 `uvm_expert_offload_release_subchunk_block()`。

如果项目最终只允许 64 KiB Expert envelope，还可以在后续把 `SUBCHUNK_64K` 从“可选 flag”改成 release ioctl 的固定语义；但这属于进一步 ABI 收敛，本项只要求删除不可达的 2 MiB strict 模式。

### 3. 删除 `max_blocks` 限制

`max_blocks` 当前存在于三层：

```text
Python API：
  driver_release_regions(..., max_blocks: int = 0)

Python ctypes ABI：
  _ExpertOffloadReleaseParams.max_blocks

内核 ioctl ABI：
  UVM_EXPERT_OFFLOAD_RELEASE_PARAMS.max_blocks
```

入口见 [Python 参数](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:1156)、[ctypes 字段](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:146) 和 [内核 ABI 字段](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_ioctl.h:1806)。

当前唯一上层调用 `release_uvm_regions()` 没有传入该参数，所以它始终为 `0`，即“不限制”。内核的限制分支位于 [uvm.c](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:11421)：达到限制后跳过后续 block、记录 `NV_ERR_INSUFFICIENT_RESOURCES`，最终得到部分 release 和 `UNKNOWN` 状态。

这与当前 Expert 原子语义冲突：

```text
策略选择的是整个 Expert
ExpertRecord 提交的是该 Expert 的全部 envelope IDs
每个 envelope 应完整 release
不能因为人工 block 上限主动留下半个 envelope
```

如果系统资源不足，应由真实的迁移失败返回错误，而不是通过 `max_blocks` 主动截断操作。上层收到失败后保持 Expert/Region 为 `UNKNOWN` 并停止进入 serving，不能把部分卸载当作正常限流。

应同步删除：

```text
driver_release_regions() 的 max_blocks 参数
params.max_blocks 的赋值
_ExpertOffloadReleaseParams ctypes 字段
UVM_EXPERT_OFFLOAD_RELEASE_PARAMS 内核字段
uvm_expert_offload_release_zero() 对 max_blocks 的保存和恢复
内核循环中的 max_blocks 判断及其人为失败记录
相关测试、注释和文档
```

`block_count` 是否保留应按第十四节的最小结果方案单独处理：它目前还参与“是否找到有效 VA block”的成功判定，不能仅因为删除 `max_blocks` 就直接删除所有 block 计数。

### 4. ABI 同步要求

删除 `max_blocks` 会修改 Python ctypes 和内核 ioctl 参数结构，必须作为一次原子变更完成：

```text
1. 修改 uvm_ioctl.h
2. 修改 uvm.c
3. 修改 Python _ExpertOffloadReleaseParams
4. 修改 driver_release_regions() 签名和调用点
5. 重新编译并重新加载 UVM 内核模块
6. 确认用户态与内核态 sizeof/字段 offset 一致
```

不能只改 Python 或只改内核。即使编译器为删除的 `NvU32` 自动补齐 padding，也不能依赖偶然布局兼容，必须显式验证 ABI。

如果需要滚动兼容旧用户态，可先把字段改名为必须为零的 `reserved0`，待所有组件升级后再物理删除；如果内核模块和 Python 始终成套部署，则可以直接同步删除。

### 5. 精简后的最小调用形式

Python 接口收敛为：

```python
def driver_release_regions(
    region_ids: Sequence[int],
    *,
    device: int = 0,
    remote_read: bool = False,
    prefer_existing: bool = True,
) -> dict[str, object]:
    ...
```

每个 ioctl 请求只输入：

```text
region_id
gpu_uuid
flags = SUBCHUNK_64K | optional REMOTE_READ
```

结合第十四节，应用层最终只接收：

```python
{
    "ok": bool,
    "statuses": dict[int, bool],
}
```

### 6. 测试和验收条件

需要增加或调整以下测试：

```text
仓库中不再出现 STRICT_2M_BLOCKS
driver_release_regions() 不再接受 max_blocks
Python ctypes 和内核 ioctl 结构布局一致
64 KiB 对齐 Region 能完整 release
跨多个 VA block 的 Region 不受人工数量上限，全部被处理
任一 block 真实失败时 Region 返回失败并置 UNKNOWN
remote_read 覆盖完整 Region，并验证 CPU residency 和 remote mapping

```

最终验收搜索：

```text

UVM_EXPERT_OFFLOAD_RELEASE_PARAMS.max_blocks     -> 0 个结果

```

## 十六、将 KV dynamic resize 收敛为单卡流程

### 1. 结论和范围

当前实验只在单卡、单 GPUWorker 上运行，[`_resize_uvm_kv_target_with_workers`](D:/github/uvm/workloads/vllm/vllm/vllm/v1/engine/core.py:478) 中为多 rank 一致性设计的大量聚合、回显校验和结果记录可以删除。

但单卡不等于 EngineCore 可以直接操作 CUDA VA。EngineCore 与 GPUWorker 仍可能位于不同进程，实际 KV tensor 和 CUDA context 由 worker 持有，因此必须保留一次 RPC：

```text
保留：EngineCore -> 唯一 GPUWorker 的一次物理迁移 RPC
删除：多个 worker/rank 之间的结果合并、交集和一致性协议
```

建议将函数重命名为：

```python
_resize_uvm_kv_target_single_worker()
```

或者直接：

```python
_resize_uvm_kv_target()
```

并在 worker/engine 初始化阶段只校验一次：

```python
if parallel_config.world_size != 1:
    raise RuntimeError("Current UVM dynamic KV resize supports one GPU only")
```

完成一次启动约束后，resize 热路径无需重复处理多卡兼容。

### 2. 当前可以删除的多卡数据结构

删除以下仅为跨 worker 聚合存在的变量：

```text
expert_candidate_results
expert_results                 # 多 worker 原始结果列表
expert_release_missing_layers  # EngineCore 跨 worker 聚合结果
worker_results                 # 多 rank 原始结果列表
rank_completed
rank_completed_cpu
rank_completed_gpu
completed_intersection
completed_cpu_intersection
completed_gpu_intersection
protocol_unknown               # 多 worker schema 不一致标志
```

删除逐 rank 循环：

```python
for worker_result in worker_results:
    ...
```

以及以下多卡一致性校验：

```text
每个 rank 回显 requested_block_ids
每个 rank 回显 requested_cpu_block_ids / requested_gpu_block_ids
每个 rank 回显 old_target_blocks / new_target_blocks
每个 rank 回显相同 plan_token
每个 rank completed 集合的子集检查
所有 rank completed 集合求交集
所有 rank 均 ok/synchronized/made_progress 的聚合判断
```

单卡情况下，EngineCore 已经持有唯一 preparation plan，worker 是该计划唯一的物理执行者，不需要让 worker 把整份输入再返回一遍供 EngineCore比较。

### 3. 保留单 worker RPC，不保留 collective 语义

底层 executor 的 `collective_rpc()` 接口可能仍返回 list。可以增加一个极小的适配入口：

```python
def _uvm_single_worker_rpc(self, method: str, *, args: tuple[Any, ...]) -> Any:
    return self.collective_rpc(method, args=args)[0]
```

worker 数量应在启动阶段验证为 1，因此这里不再循环、不再合并结果，也不把 list 继续传播到 resize 控制逻辑。

如果底层提供单 worker RPC，应直接使用它；在此之前使用 `[0]` 只是进程边界适配，不代表保留多卡策略。

### 4. 精简增量 Expert wave

KV grow 前释放一轮 Expert 的顺序仍需保留：

```text
查询唯一 worker 的 cold candidate
  -> 若没有 cold，再查询 warm candidate
  -> 唯一 worker release 所选 Expert
  -> 成功后才继续 KV grow
```

删除 `_select_uvm_incremental_experts_by_layer()` 中“跨 worker 对同层候选取最小 global expert ID”的合并逻辑。唯一 worker 可直接返回：

```python
{
    "ok": bool,
    "candidates": dict[str, int],  # layer_key -> global_expert_id
}
```

不再返回或保存：

```text
reason = candidates_collected
expert_class 回显
candidate_count
每个 candidate 的重复 layer_name/layer_id
所有 worker 的 candidate_results
```

`run_uvm_incremental_expert_offload()` 应在 worker 内部确认所有传入的 `layer_key -> expert_id` 都已经完成 release，最小返回：

```python
{"ok": bool}
```

因此 EngineCore 可以删除 `_uvm_incremental_release_missing_layers()` 以及 `results/visited_layers/selected_layers/released_count` 等诊断字段。若任一层未完成，worker 直接返回 `ok=False`，不能由 EngineCore 再从大字典中推导。

`selected_expert_class` 和 `selected_experts_by_layer` 仅作为当前调用的局部控制变量，不再加入最终返回值。

### 5. 单 worker 物理迁移的最小协议

当前 [`resize_uvm_kv_cache_target`](D:/github/uvm/workloads/vllm/vllm/vllm/v1/worker/gpu_model_runner.py:4978) 返回大量输入回显、完成集合和调试信息。单卡协议可收敛为：

```python
{
    "ok": bool,
    "made_progress": bool,
}
```

含义固定为：

```text
ok=True：
  本次 plan 要求的全部 CPU/GPU range 均已迁移
  必要的 CUDA synchronize 已成功

ok=False, made_progress=False：
  没有任何物理迁移提交，可以安全回滚 queue quarantine

ok=False, made_progress=True：
  已提交或可能已提交部分迁移
  不能把 block 重新暴露给 scheduler
  所有 plan block 保持 offline 并标记 UNKNOWN，等待 reconciliation
```

因此 worker 不再返回：

```text
reason
old_target_blocks / new_target_blocks
block_count
requested_block_ids
requested_cpu_block_ids / requested_gpu_block_ids
completed_block_ids
completed_cpu_block_ids / completed_gpu_block_ids
plan_token
synchronized
direction_results
range_count / range_bytes / successes
executor
driver_result / advise_result / prefetch_result
elapsed_seconds
```

`synchronized` 不需要单独返回：worker 只有在迁移完整且同步成功后才能返回 `ok=True`。同步失败必须返回 `ok=False, made_progress=True`。

完成 ID 也不需要跨进程返回：单 worker 的 `ok=True` 契约代表完整 plan 成功；若失败且发生过进度，finalize 对整个 plan 做保守隔离，而不是尝试从部分完成列表推断可重新分配的 block。

### 6. preparation/finalize 的单卡收敛

以下事务边界不是多卡逻辑，必须保留：

```text
prepare：先把 shrink/grow 涉及的 block 从 scheduler 可分配 queue 隔离
physical RPC：唯一 worker 执行 VA range 搬运和同步
finalize success：提交 LogicalKVBlock 状态和 applied target
finalize no-progress failure：回滚新隔离的 queue membership
finalize progress failure：保持隔离，将相关 block 标记 UNKNOWN
```

`prepare_external_dynamic_pool_resize()` 可重命名为：

```python
prepare_dynamic_pool_resize()
```

`finalize_external_dynamic_pool_resize()` 可重命名为：

```python
finalize_dynamic_pool_resize()
```

单卡 finalize 只接收：

```python
finalize_dynamic_pool_resize(
    preparation,
    block_pool=block_pool,
    worker_ok=bool(worker_result["ok"]),
    worker_made_progress=bool(worker_result["made_progress"]),
)
```

不再接收三个 completed-ID 列表、worker metadata 或原始 worker result。

`preparation` 仍可在应用层内部保存正确性所需的：

```text
old_target
new_target
transition block IDs
CPU/GPU 方向
newly quarantined block IDs
已有 dirty/reconciliation IDs
generation
```

这些字段不应被拼进公开返回值或日志。`generation` 只用于 EngineCore 本地 prepare/finalize 期间防止计划被并发修改，不需要让唯一 worker 回显 `plan_token`。

### 7. 推荐的单卡主流程

```python
def _resize_uvm_kv_target(
    self,
    target_blocks: int,
    *,
    reason: str,
    release_expert_wave: bool,
) -> dict[str, Any]:
    components = self._uvm_dynamic_pool_components()
    if components is None:
        return {"ok": False, "reason": "dynamic_pool_unavailable"}

    policy, block_pool = components
    old_target = int(policy._dynamic_pool_applied_target_blocks)
    target = min(max(int(target_blocks), 0), int(policy.total_blocks))
    dirty_ids = policy.get_dynamic_pool_reconciliation_block_ids()

    if target == old_target and not dirty_ids:
        return {"ok": True, "reason": "already_at_target"}
    if target < old_target and self.scheduler.has_unfinished_requests():
        return {"ok": False, "reason": "scheduler_busy"}

    if release_expert_wave and target > old_target:
        candidates = self._uvm_single_worker_rpc(
            "get_uvm_incremental_expert_offload_candidates",
            args=("cold",),
        )
        if not candidates["ok"]:
            return {"ok": False, "reason": "expert_selection_failed"}
        allow_warm = not candidates["candidates"]
        if allow_warm:
            candidates = self._uvm_single_worker_rpc(
                "get_uvm_incremental_expert_offload_candidates",
                args=("warm",),
            )
        if not candidates["ok"]:
            return {"ok": False, "reason": "expert_selection_failed"}
        if candidates["candidates"]:
            released = self._uvm_single_worker_rpc(
                "run_uvm_incremental_expert_offload",
                args=(allow_warm, candidates["candidates"]),
            )
            if not released["ok"]:
                return {"ok": False, "reason": "expert_release_failed"}

    if (
        not policy.dynamic_pool_physical_migration_enable
        and not policy._dynamic_pool_external_reconciliation_required
    ):
        result = self._apply_uvm_kv_dynamic_pool_target(
            target,
            policy=policy,
            block_pool=block_pool,
            reason=reason,
        )
        return {
            "ok": bool(result["ok"]),
            "reason": str(result.get("reason") or "apply_failed"),
        }

    preparation = policy.prepare_dynamic_pool_resize(
        target,
        block_pool=block_pool,
        reason=reason,
    )
    if not preparation["ok"]:
        return {"ok": False, "reason": "prepare_failed"}

    try:
        worker = self._uvm_single_worker_rpc(
            "resize_uvm_kv_cache_target",
            args=(old_target, target, dirty_ids),
        )
    except Exception:
        # RPC 异常不能证明 worker 未提交迁移，必须保守处理。
        worker = {"ok": False, "made_progress": True}

    finalized = policy.finalize_dynamic_pool_resize(
        preparation,
        block_pool=block_pool,
        worker_ok=bool(worker["ok"]),
        worker_made_progress=bool(worker["made_progress"]),
    )
    if not finalized["ok"]:
        return {"ok": False, "reason": "physical_migration_failed"}
    return {"ok": True, "reason": "applied"}
```

该伪代码保留了 resize 的事务正确性，但不再保存和传播多 worker 原始数据。

## 十七、目标方案：GPU-online / GPU-backup / CPU-offline 三队列

### 1. 评估结论

该方案在控制思想和数据结构上可行，可以作为当前两队列 dynamic KV pool 的下一阶段目标。它本质上是“受 read-ahead 启发的 GPU 驻留容量预取”：

```text
GPU-online：
  已在 GPU，可被 scheduler 立即分配

GPU-backup：
  已完成 GPU prefetch，但对 allocator 不可见
  online 容量不足时只做队列 promotion，不做 CPU->GPU 搬运

CPU-offline：
  已确认在 CPU，对 allocator 不可见

PREFETCHING_CPU / PREFETCHING_GPU：
  迁移中的状态，不建立第四条可分配队列
```

方案能够解决当前两队列模型的一个核心延迟问题：现有 grow 必须先等待 `offline -> GPU` 搬运完成，才能把 block 暴露给 scheduler；引入已经 GPU-resident 的 backup 后，紧急 grow 可以先通过 `backup -> online` 立即增加可分配容量，再在后台补充下一轮 backup。

但当前代码尚未实现该能力：

```text
BlockPool 目前只有 free_block_queue 和 offline_block_queue
当前 worker resize 会等待 CUDA synchronize 后才返回
当前 offline queue 同时承担 CPU、quarantine 和 UNKNOWN
UVM prefetch 完成不等于页面会永久 pin 在 GPU
```

因此应把本节视为需要实施的新架构，而不是对当前实现的描述。

### 2. 与磁盘 read-ahead 的准确关系

可以采用以下类比：

| 磁盘/文件预读 | KV cache 三队列 |
| --- | --- |
| backing storage | CPU-offline KV blocks |
| 当前 page-cache 窗口 | GPU-online blocks |
| look-ahead window | GPU-backup blocks |
| readahead marker | online 低水位 |
| 扩大窗口 | 增加下一轮 backup refill 数量 |
| 页面消费速度 | KV block 净分配速度 |

共同点是提前把慢速层的数据放入快速层，并根据消费速度调整窗口；区别是 KV block 是 GPU 可写工作区，预测目标是未来容量，而不是连续文件地址。文档中应使用：

```text
受 read-ahead 启发的驻留容量预测
```

不应声称它与 Linux 文件 read-ahead 完全相同。

### 3. 三队列只管理空闲 block

三条队列保存的都必须是：

```text
ref_cnt == 0
is_null == False
当前没有请求使用
```

active block 不属于任何空闲队列：

```text
active block:
  ref_cnt > 0
  free_queue_kind = None
```

建议把 [BlockPool](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/block_pool.py:165) 扩展为：

```python
self.free_block_queue = FreeKVCacheBlockQueue(...)     # GPU-online
self.backup_block_queue = FreeKVCacheBlockQueue([])   # GPU-backup
self.offline_block_queue = FreeKVCacheBlockQueue([])  # CPU-offline
```

对应 membership：

```text
free_queue_kind = "gpu"
free_queue_kind = "backup"
free_queue_kind = "offline"
free_queue_kind = None
```

`get_num_free_blocks()` 只能返回 `free_block_queue.num_free_blocks`。backup 虽然在 GPU，但在 promotion 前绝不能被普通 allocation 计入可用容量。

### 4. PREFETCHING 不建立第四条队列

如果把 `CPU-offline` 严格定义成“已经 CPU resident”，正在迁移或状态不确定的 block 就不能继续混在 offline queue 中。建议：

```text
开始 CPU->GPU：
  从 offline queue 移除
  free_queue_kind = None
  LogicalKVBlock.state = PREFETCHING_GPU
  block_id 加入 _kv_prefetch_inflight

完成 CPU->GPU：
  从 inflight 集合移除
  LogicalKVBlock.state = GPU
  加入 backup queue

开始 GPU->CPU：
  从 online/backup queue 移除
  free_queue_kind = None
  LogicalKVBlock.state = PREFETCHING_CPU
  block_id 加入 _kv_offload_inflight

完成 GPU->CPU：
  从 inflight 集合移除
  LogicalKVBlock.state = CPU
  加入 offline queue
```

迁移发生部分失败时：

```text
LogicalKVBlock.state = UNKNOWN
free_queue_kind = None
block 保持 quarantine，不允许 scheduler 分配
等待 reconciliation 后再进入三条稳定队列之一
```

这样仍然只有三条稳定队列，`PREFETCHING_*` 和 `UNKNOWN` 由状态加 inflight/quarantine 集合表达。

### 5. 必须分离 queue membership 与 residency state

最小模型应同时保存两个正交维度：

```text
queue membership：
  online / backup / offline / none

physical residency：
  GPU / CPU / PREFETCHING_GPU / PREFETCHING_CPU / UNKNOWN
```

合法稳定组合为：

```text
online  + GPU
backup  + GPU
offline + CPU
none    + PREFETCHING_GPU/PREFETCHING_CPU/UNKNOWN
none    + GPU/CPU 且 ref_cnt>0                # active block
```

禁止：

```text
online + CPU
backup + CPU
offline + GPU
任何 ref_cnt>0 block 出现在 backup/offline queue
```

`free_queue_kind` 不能被当成物理驻留证明；`LogicalKVBlock.state` 也不能单独决定 scheduler 是否可分配。

### 6. 初始容量计算修正

初始公式可以保留，但 `S_block` 必须表示“一个逻辑 block 在本 GPU 上跨全部 KV PhysicalKVSpan 占用的总字节数”，不能只取某一层或某个 tensor 的 page size：

```text
S_logical_block =
  对本 GPU 上属于同一个 block_id 的所有 group/layer/tensor page bytes 求和
```

GPU 可驻留 KV block 上限：

$$
N_{GPU,max}
=
\left\lfloor
\frac{M_{GPU}-M_{fixed}-M_{guard}}{S_{logical\_block}}
\right\rfloor.
$$

初始 online：

$$
N_0=\left\lceil\frac{C_0L_0}{B}\right\rceil.
$$

初始 backup：

$$
W_0=\left\lceil\rho N_0\right\rceil,
\qquad \rho\in\{0.125,0.25\}.
$$

必须满足：

$$
N_0+W_0\le
\min(N_{GPU,max},N_{total\_blocks}).
$$

初始化进入 serving 前必须完成：

```text
online + backup 的所有 PhysicalKVSpan ranges prefetch 到 GPU
CUDA synchronize 成功
其余 free blocks 完整迁移到 CPU
三队列 membership 和 LogicalKVBlock state 提交完成
```

不能仅通过修改队列字段假装 backup 已经 GPU resident。

### 7. grow 触发条件

在 [KVCacheManager 分配检查](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/kv_cache_manager.py:278) 得到本轮新增需求 `R_t` 后、比较 free block 数之前，计算：

```text
F_t = online free queue 数量
R_t = 本轮预计新增 block 数量
H_t = 当前低水位
```

第一阶段可采用用户提出的简单条件：

$$
F_t-R_t\le H_t,
\qquad H_t=W_0.
$$

该条件正确但只是初始启发式。后续可把 `H_t` 调整为当前消费速率或 backup 窗口的函数；第一版不要同时引入复杂预测器。

同一时刻只允许一个 backup refill：

```text
if refill_inflight:
  不再发起第二轮 refill
```

### 8. backup promotion 必须是原子元数据操作

低水位触发后，先执行：

```text
从 backup_block_queue 移除 ready blocks
更新 free_queue_kind = "gpu"
加入 free_block_queue
```

该操作必须发生在 scheduler/EngineCore 的串行控制线程中，使 scheduler 不可能观察到半次 promotion。

如果整个 backup 窗口均已确认 GPU resident，可以一次 promotion 全部 backup。也可以只 promotion 满足本轮需求和低水位的数量：

$$
P_t=
\min\left(
|backup|,
\max(0,R_t+H_t-F_t)
\right).
$$

第一版使用“promotion 全部 backup”更简单；性能稳定后再评估按需 promotion。

promotion 后 allocation 仍然只能从 `free_block_queue` 执行，现有 [get_new_blocks](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/block_pool.py:316) 不需要知道 CPU-offline block。

### 9. 下一轮 refill 数量必须受剩余 HBM 限制

不能只使用：

$$
W_{t+1}=\min(2W_t,W_{max}).
$$

因为 online 会随着每次 promotion 持续增长，必须把当前 online 已占容量计入上限。正确的 refill 数量应为：

$$
W_{refill}
=
\min\left(
2W_t,
W_{max},
N_{GPU,max}-N_{online\_after\_promotion},
N_{offline\_available}
\right).
$$

同时满足：

```text
W_refill > 0
没有 refill 正在执行
共享 HBM controller 允许增加 KV 驻留
必要的 Expert release wave 已成功
```

如果没有剩余 HBM，停止扩大窗口；不能依靠 UVM 自动挤出 Hot Expert 来制造 backup。

### 10. 真正异步 refill 需要新的 worker 状态机

当前 [`resize_uvm_kv_cache_target`](D:/github/uvm/workloads/vllm/vllm/vllm/v1/worker/gpu_model_runner.py:4978) 在迁移后执行 CUDA synchronize，再同步返回 EngineCore。因此直接复用当前调用只能实现：

```text
backup promotion 很快
但 refill 会阻塞后续 EngineCore 调度
```

这在功能上正确，但不能完整隐藏 CPU->GPU 延迟。真正 read-ahead 需要拆成：

```text
begin_backup_refill(block_ids)
  -> worker 在专用 CUDA stream 提交 prefetch
  -> 返回 operation_id

poll_backup_refill(operation_id)
  -> pending / complete / failed

finalize_backup_refill(operation_id)
  -> CUDA event 已完成后提交 LogicalKVBlock=GPU
  -> 将 block 加入 backup queue
```

CUDA event 由 worker 进程保存，不能让 EngineCore 直接持有无效的跨进程 CUDA event。EngineCore 只保存轻量 `operation_id` 并在 scheduler tick 或后台控制周期轮询。

第一阶段可以先实现同步 refill 验证三队列正确性；第二阶段再引入 begin/poll/finalize 异步协议。不能把同步 RPC 描述成已实现的异步 read-ahead。

### 11. UVM backup 驻留保证

`cudaMemPrefetchAsync(..., GPU)` 加同步只能证明同步点时迁移已完成，不能把 managed page 永久 pin 在 GPU。之后如果 HBM 超额或其他 allocation 造成压力，UVM 仍可能把 backup 页挤到 CPU。

因此“backup -> online 绝不发生物理搬运”成立需要至少满足：

```text
online + backup + Hot Expert + fixed/workspace 不超过严格 HBM budget
backup refill 完成后才写 state=GPU
所有新增 KV/Expert placement 都通过同一个容量控制器
发生超预算或未知迁移后使 backup state 失效
只 promotion state=GPU 且不在 inflight/UNKNOWN 的 block
```

在受控单卡实验中，可用严格预算和同步后的状态作为软驻留保证。若目标是严格的延迟保证，还需要以下至少一种机制：

```text
驱动级 pin/residency reservation
promotion 前批量 residency query 并在失败时重新 prefetch
不允许被 UVM 自动迁移的独立 GPU allocation
```

没有这些约束时，功能仍可能借助 UVM page fault 正确运行，但“promotion 无搬运、立即可用”的性能保证不成立。

### 12. online 不足时的正确行为

如果：

```text
F_t < R_t
backup 为空或不足
refill 尚未完成
```

scheduler 不能直接分配 CPU-offline writable KV。必须选择一种已有安全行为：

```text
推迟该请求到下一轮
执行 preemption/backpressure
等待当前 refill 完成后再分配
```

不能把 `PREFETCHING_GPU` 或 `CPU` block 提前放进 online queue。

### 13. 稳态不会错误扩容

请求结束后，active block 通过 `free_blocks()` 回到 online free queue。若 block 分配和回收达到稳态，则：

$$
F_t-R_t>H_t.
$$

不会触发 promotion/refill。因此该条件实际测量的是 online free block 的净消耗，而不是单纯请求并发数。

为了防止一个调度周期重复触发，需要保存：

```text
last_promotion_epoch
refill_inflight
```

这些是控制状态，不是调试记录。

### 14. shrink 方案

缩容采用滞后检查是可行的。初始参数可以为：

```text
T_check = 1 秒
K = 3 次
online 空闲率阈值 = 50%
最低 online = N0
最低 backup window = W0
```

触发条件：

```text
连续 K 个周期没有 promotion/grow
online_free / online_total >= 0.5
online_total > N0
当前没有 refill/offload 操作
```

窗口缩小：

$$
W_{t+1}
=
\max\left(W_0,\left\lfloor\frac{W_t}{2}\right\rfloor\right).
$$

但实际 online shrink 数不能简单固定为 `W_{t+1}`，还必须满足：

```text
只选择 ref_cnt=0 的 online block
不能使 online_total 低于 N0
不能使剩余 online free 低于安全水位
优先选择连续 partition 尾部的 block，保持现有 block-id target 模型
边界 block active 时延迟本轮 shrink，不移动 active block
```

若 backup 数量大于新窗口，先把多余 backup 从 queue 移除并迁移到 CPU；成功后加入 offline。随后再按容量目标选择 online free block 做 GPU->CPU 迁移。

所有 shrink block 必须先从可分配队列移除，再开始物理迁移。

### 15. BlockPool 需要同步修改的位置

新增第三条队列后，至少需要修改：

```text
BlockPool.__init__()                 # 创建 backup_block_queue
_remove_from_current_free_queue()    # 支持 backup membership
get_num_free_blocks()                # 只统计 online
get_new_blocks()                     # 只从 online 分配
free_blocks()                        # 按目标 partition/state 返回正确队列
touch()/prefix-cache lookup          # backup/offline 不可直接命中分配
reset_prefix_cache()                 # 统计三队列和 inflight
get_usage()                          # 明确 online utilization 与 GPU residency utilization
dynamic target transition           # online/backup/offline 三向移动
```

建议保持连续 block-id partition：

```text
[1, online_end]                         online/active
[online_end + 1, backup_end]            backup
[backup_end + 1, total_blocks]          offline
```

promotion 和 refill 只移动 partition 边界，可继续复用 PhysicalKVSpan 的 `block_id -> VA range` 映射。若允许任意稀疏 block membership，则 `_dynamic_pool_applied_target_blocks` 单一边界不再够用，需要更大范围重构。

### 16. 最小运行时状态

三队列第一版只需新增以下控制状态：

```text
online_end / online_target_blocks
backup_end / backup_target_blocks
window_blocks W_t
low_watermark H_t
refill_inflight operation_id | None
prefetching block IDs
offloading block IDs
UNKNOWN reconciliation block IDs
连续低利用周期计数
last promotion/grow epoch
```

不需要保存：

```text
每轮完整 worker result
所有历史窗口
地址 dump
逐 range 调试统计
每次 promotion 的详细日志
```

### 17. 分阶段实施顺序

```text
阶段 A：三条稳定队列，迁移仍同步
  增加 backup queue 和严格状态不变量
  初始化 online/backup/offline placement
  实现 backup -> online promotion
  refill 使用现有同步 worker RPC
  验证 scheduler 永不分配 CPU/PREFETCHING/UNKNOWN block

阶段 B：窗口控制
  加入 F-R<=H 低水位
  加入 W 倍增及严格 HBM cap
  加入低利用 K 周期 shrink

阶段 C：真正异步 read-ahead
  worker begin/poll/finalize API
  专用 CUDA stream/event
  EngineCore 非阻塞 refill 状态机

阶段 D：驻留保证增强
  统一 KV/Expert HBM budget
  residency query 或 driver reservation
  超预算时 backup 失效与回收
```

### 18. 验收条件

```text
BlockPool 明确存在 online、backup、offline 三条稳定队列
只有 online queue 计入 scheduler free capacity
backup promotion 不调用任何 CPU->GPU 搬运函数
只有已完成 GPU prefetch 和 synchronize 的 block 能进入 backup
PREFETCHING/UNKNOWN block 不在任何可分配队列
ref_cnt>0 block 永不进入 backup/offline 或参与 shrink
offline block 永不直接分配给 attention kernel
任一时刻最多一个 backup refill
online+backup 不超过 KV GPU residency budget
部分迁移失败时 block 保持 UNKNOWN quarantine
无进度失败能够回滚原队列
稳定分配/回收循环不会持续扩容
持续净消耗会 promotion backup 并补充下一窗口
低利用连续 K 周期后才缩容，且不低于 N0/W0
异步阶段中 scheduler 在 refill 进行时仍能使用已 promotion 的 online block
```

最终目标调用链为：

```text
scheduler 计算 R_t
  -> 检查 online 低水位
  -> 原子 promotion backup -> online
  -> 正常分配 online block
  -> 后台提交 offline -> PREFETCHING_GPU
  -> CUDA event 完成
  -> PREFETCHING_GPU -> backup
```

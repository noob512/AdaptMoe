# 修改方案：KV 动态池精简、内核 Region 收敛与 Hot Expert 驻留修正

本文档只描述后续修改方案，不代表运行时代码已经完成修改。目标是删除不参与正确性控制的记录与旧语义字段，同时保留迁移、幂等、失败恢复和初始化驻留所必需的最小状态。

# 一、精简 `_ensure_dynamic_pool_applied()`

## 1. 结论

当前函数同时承担三类工作：

1. 动态 KV pool 的正确性控制；
2. block queue、物理迁移和 LogicalKVBlock 状态提交；
3. 诊断记录、统计计数和嵌套结果组装。

第 3 类可以删除。第 1、2 类不能删除，否则会破坏 active block 保护、迁移失败回滚和 scheduler 可分配 block 边界。

建议将函数收敛为：

```text
检查目标
  -> 计算变化区间
  -> shrink 时确认 block 全部空闲
  -> 调用 queue 隔离/恢复
  -> 执行或确认物理迁移
  -> 成功后提交 LogicalKVBlock 和 applied target
  -> 只返回 ok/reason
```

## 2. 可以删除的代码

### 2.1 纯统计计数

以下变量只在 debug record 中使用，不参与控制决策：

```python
offloaded = 0
prefetched = 0
skipped_active = 0
```

删除后，以下调用不再需要通过返回值累计数量：

```python
if self._mark_dynamic_pool_block_cpu(...):
    offloaded += 1

if self._mark_dynamic_pool_block_gpu(...):
    prefetched += 1
```

直接调用即可：

```python
self._mark_dynamic_pool_block_cpu(block=block)
self._mark_dynamic_pool_block_gpu(block=block)
```

如果这两个 helper 在其他调用点也不需要布尔返回值，可以进一步改成返回 `None`，并删除当前未使用的 `reason/old_target/new_target` 参数。

### 2.2 `queue_result` 诊断字典

`block_pool.apply_uvm_dynamic_pool_target()` 的队列移动副作用必须保留，但返回的统计字典在当前函数中只用于 debug 输出：

```text
moved_gpu
moved_offline
deferred_active
gpu_free_blocks
offline_free_blocks
```

因此可由：

```python
queue_result = block_pool.apply_uvm_dynamic_pool_target(...)
```

改成：

```python
block_pool.apply_uvm_dynamic_pool_target(...)
```

active block 失败分支和 grow 失败分支中手工构造的 `queue_result` 字典可以直接删除。

### 2.3 pressure snapshot

以下内容仅用于统一 residency trace：

```python
pressure_record = {...}
pressure_record.update(...)
record_unified_residency_snapshot(
    reason="kv_dynamic_pool_resize",
    kv_pressure=pressure_record,
)
```

它不决定 target、队列移动、物理迁移或 LogicalKVBlock 状态，可以从该函数删除。

如果整个 KV runtime 不再需要该 trace，还可继续删除：

```text
dynamic_pool_debug_records_enable
VLLM_UVM_KV_DYNAMIC_POOL_DEBUG_RECORDS_ENABLE
对应 record_config() 字段
仅为这些记录保留的 time/driver detail
```

本方案第一阶段只删除当前函数的 snapshot 调用，避免同时扩大修改范围。

### 2.4 debug 返回字段

以下返回内容没有仓库内功能调用者：

```text
direction
desired_target_blocks
queue_transition
physical_migration
deferred_active_blocks
```

`apply_unified_kv_target_blocks()` 只读取 `ok/reason`，另一个调用点忽略返回值。因此 `_ensure_dynamic_pool_applied()` 最小返回契约可收敛为：

```python
{"ok": bool, "reason": str}
```

`applied_target_blocks` 已保存在：

```python
self._dynamic_pool_applied_target_blocks
```

上层 `apply_unified_kv_target_blocks()` 也会单独返回该属性，不需要在嵌套 `apply_result` 中重复保存。

## 3. 必须保留的逻辑

以下部分不是调试代码，不能删除。

### 3.1 启用状态和幂等检查

```python
if not self.dynamic_pool_active() or block_pool is None:
    ...

if old_target == target:
    ...
```

作用是避免未启用时修改 scheduler，并跳过重复 resize。

### 3.2 candidates 范围计算

```python
first_block = min(old_target, target) + 1
last_block = max(old_target, target)
candidates = ...
```

这是 target delta 到具体 block 的映射，必须保留。

### 3.3 shrink 前 active block 检查

```python
active_candidates = [
    block for block in candidates
    if not self._dynamic_pool_block_safe_for_resize(block)
]
```

这是正确性保护。仍在被请求引用的 KV block 不能进入 offline queue，也不能迁移到 CPU。

可以删除 active block ID 的诊断列表，但不能删除 `active_candidates` 判断。

### 3.4 queue 隔离和失败回滚

shrink 必须遵循：

```text
先把 free block 从 GPU free queue 移到 offline queue
再执行物理迁移
```

否则物理迁移期间 scheduler 可能重新分配这些 block。

当迁移完全没有产生物理进度时，必须把 queue target 回滚。发生部分迁移时不能直接回滚，否则 scheduler 可能重新分配一个已经部分处于 CPU 的 block。

### 3.5 物理迁移

以下调用必须保留：

```python
self._migrate_dynamic_pool_physical_blocks(...)
```

`external_physical_ready=True` 也必须保留，因为 EngineCore 可以先让 worker 完成物理迁移，再在 scheduler 进程提交 queue 和 logical state。

`dynamic_pool_physical_migration_enable=False` 的逻辑-only 模式同样应保持当前行为。

### 3.6 状态提交

只有物理阶段成功或明确由外部完成后，才能执行：

```python
self._mark_dynamic_pool_block_cpu(...)
self._mark_dynamic_pool_block_gpu(...)
self._dynamic_pool_applied_target_blocks = target
```

这些操作决定 LogicalKVBlock 状态和 scheduler 看到的有效 pool 大小，不是统计信息。

## 4. 必须同时修正的返回契约问题

当前 `_ensure_dynamic_pool_applied()` 用下面的字段判断 shrink 失败后能否回滚：

```python
physical_result.get("successes")
```

但 `_migrate_dynamic_pool_physical_blocks()` 只在：

```python
self.dynamic_pool_debug_records_enable
```

为真时才把 `successes` 放进返回值。debug 关闭时，即使已经发生部分迁移，上层也会把缺失字段当成 `0`，可能错误回滚 queue。

因此不能简单删除整个 `physical_result`。应把迁移返回契约收敛为与 debug 无关的最小结果：

```python
{
    "ok": bool,
    "reason": str,
    "made_progress": bool,
}
```

其中：

```python
made_progress = int(successes) > 0
```

`range_count/range_bytes/executor/elapsed_seconds/driver_result` 全部可以删除。

进一步建议：当前 helper 在部分成功时会把所有目标 LogicalKVBlock 都写成 CPU/GPU，但底层 `successes` 是 range 级计数，无法证明每个 block 都完成。保守做法是：

```text
全部 range 成功：提交目标 logical state
零进度失败：允许 queue 回滚
部分成功：保持 offline quarantine，logical state 标 UNKNOWN，不提交 applied target
```

## 5. 推荐的精简结构

建议增加一个内部 helper，将外部完成、逻辑-only 和真实物理迁移统一成最小结果：

```python
def _dynamic_pool_migration_outcome(...):
    if external_physical_ready:
        return {"ok": True, "reason": "external_complete", "made_progress": True}
    if not self.dynamic_pool_physical_migration_enable:
        return {"ok": True, "reason": "logical_only", "made_progress": False}
    return self._migrate_dynamic_pool_physical_blocks(...)
```

精简后的主函数伪代码：

```python
def _ensure_dynamic_pool_applied(...):
    if not active or block_pool is None:
        return {"ok": False, "reason": "unavailable"}

    target = self.dynamic_pool_target_blocks
    old_target = self._dynamic_pool_applied_target_blocks
    if target == old_target:
        return {"ok": True, "reason": "already_applied"}

    candidates = blocks_in_delta(old_target, target)

    if target < old_target:
        if any(not safe(block) for block in candidates):
            return {"ok": False, "reason": "active_blocks_must_drain"}

        block_pool.apply_uvm_dynamic_pool_target(
            target,
            old_target_blocks=old_target,
        )
        outcome = migrate_or_confirm(candidates, "shrink")
        if not outcome["ok"]:
            if not outcome["made_progress"]:
                block_pool.apply_uvm_dynamic_pool_target(
                    old_target,
                    old_target_blocks=target,
                )
            return {"ok": False, "reason": outcome["reason"]}

        for block in candidates:
            self._mark_dynamic_pool_block_cpu(block=block)

    else:
        safe_candidates = [block for block in candidates if safe(block)]
        outcome = migrate_or_confirm(safe_candidates, "grow")
        if not outcome["ok"]:
            return {"ok": False, "reason": outcome["reason"]}

        for block in safe_candidates:
            self._mark_dynamic_pool_block_gpu(block=block)
        block_pool.apply_uvm_dynamic_pool_target(
            target,
            old_target_blocks=old_target,
        )

    self._dynamic_pool_applied_target_blocks = target
    return {"ok": True, "reason": "applied"}
```

## 6. 涉及的入口

- 当前函数：[_ensure_dynamic_pool_applied](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/uvm_kv_runtime_policy.py:796)
- 物理迁移：[_migrate_dynamic_pool_physical_blocks](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/uvm_kv_runtime_policy.py:687)
- queue 迁移：[apply_uvm_dynamic_pool_target](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/block_pool.py:558)
- 公开调用入口：[apply_unified_kv_target_blocks](D:/github/uvm/workloads/vllm/vllm/vllm/v1/core/uvm_kv_runtime_policy.py:389)

## 7. 实施顺序

1. 先把物理迁移返回值改成固定的 `ok/reason/made_progress`。
2. 修正 partial migration 的 logical state 和 queue rollback 行为。
3. 删除 `pressure_record`、snapshot 和 debug `result.update()`。
4. 删除 `queue_result` 保存，但保留 queue 操作。
5. 删除 offloaded/prefetched/skipped 计数。
6. 将 `_ensure_dynamic_pool_applied()` 返回值收敛为 `ok/reason`。
7. 最后删除失去调用者的 debug 配置和 import。

## 8. 验收条件

```text
target 不变时不发生迁移
active block 存在时 shrink 被拒绝
shrink 前 block 先进入 offline queue
零进度失败时 queue 正确回滚
部分迁移失败时 block 保持 quarantine
完全成功后才更新 applied target
grow 成功后 block 才回到 GPU free queue
external_physical_ready 路径不重复搬运
debug 开关开/关不再改变控制行为
```

# 二、删除内核 Region 的旧语义字段

## 1. 结论

当前显式 Region 注册接口实际只接收：

```text
region_id
base
length
```

入口见 [UVM_PHASE_F_REGISTER_REGION_PARAMS](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_ioctl.h:1068) 和 [uvm_api_phase_f_register_region](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:6686)。注册函数随后把旧字段初始化为：

```text
pool = UNKNOWN
layer_id = 0
expert_id = 0
role = 0
flags = 0
state = UNKNOWN
priority = 0
last_access_epoch = 0
```

其中前五项以及 `priority/last_access_epoch` 对“应用层选择 Region、内核按 Region ID 执行搬运”的最终模型没有意义，可以删除；`state` 不能删除。

最终职责边界应为：

```text
应用层：
  决定卸载/恢复哪个 Expert
  保存 Expert -> envelope_region_ids
  做 hot/cold/active/预算判断
  向驱动提交明确的 region_id 列表

内核层：
  保存 region_id -> base/length/state
  对指定 region_id 执行 release/restore
  依据 state 跳过重复操作并维护状态转换
```

内核不再根据 `pool/layer_id/expert_id/role/flags` 识别、筛选或选择 Expert，也不再自行扫描 Region 选择 victim。

## 2. 最终保留的最小 Region 数据

建议最终将 [uvm_phase_f_region_t](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_va_space.h:62) 收敛为：

```c
typedef struct
{
    NvU64 region_id;
    NvU64 base;
    NvU64 length;
    uvm_range_tree_node_t va_node;
    NvU32 state;
} uvm_phase_f_region_t;
```

各字段作用：

```text
region_id：应用层提交的稳定句柄
base：迁移范围起始 VA
length：迁移范围长度
va_node：当前 range tree 的索引节点，不含业务语义
state：最近一次显式搬运结果和幂等判断依据
```

如果后续同步删除所有 by-VA 查询、fault 分类和重叠范围索引，`va_node` 还可以在独立阶段评估；本次不要顺带删除，以免扩大正确性风险。

`state` 至少需要支持：

```text
UNKNOWN
GPU
CPU
PREFETCHING_GPU
PREFETCHING_CPU
```

典型状态机：

```text
release(region_id):
  CPU                 -> skip/success
  GPU                 -> PREFETCHING_CPU -> CPU
  UNKNOWN             -> 查询或执行保守收敛；失败仍为 UNKNOWN

restore(region_id):
  GPU                 -> skip/success
  CPU                 -> PREFETCHING_GPU -> GPU
  UNKNOWN             -> 不得仅凭逻辑记录跳过
```

这里的 `state` 表示最近一次显式 placement 的结果，并不是持续实时的物理页驻留证明；Hot Expert 的初始化保证见第三部分。

## 3. 可以删除的字段

完成依赖迁移后，从 `uvm_phase_f_region_t` 删除：

```text
pool
layer_id
expert_id
role
flags                 # Region 的语义 flags
priority
last_access_epoch
```

并删除 `uvm_api_phase_f_register_region()` 中对应的零值初始化：

```c
region->pool = UVM_PHASE_N_POOL_UNKNOWN;
region->layer_id = 0;
region->expert_id = 0;
region->role = 0;
region->flags = 0;
region->priority = 0;
region->last_access_epoch = 0;
```

保留：

```c
region->state = UVM_PHASE_N_REGION_STATE_UNKNOWN;
```

若重命名旧的 `UVM_PHASE_N_REGION_STATE_*` 枚举，可同时将其收敛为通用 `UVM_REGION_STATE_*`，但这只是命名清理，不应改变状态机。

## 4. 不能直接一步删除的原因

这些旧字段目前仍有真实引用，并非只存在于初始化语句中。例如：

- reserved-prefetch slot 仍保存 `expert_id/role`，见 [uvm.c](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm.c:580)；
- reserved Expert 判断仍依赖 `pool/role/flags`，见 [uvm_va_space.c](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_va_space.c:80)；
- Stage-A/fault 分类仍读取 `pool/flags`，见 [uvm_va_block.c](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_va_block.c:16780)；
- GPU fault 统计仍读取 `pool/role`，见 [uvm_gpu.c](D:/github/uvm/kernel-module/nvidia-module/kernel-open/nvidia-uvm/uvm_gpu.c:2049)；
- Phase-N pool budget、自动 reclaim、query 和 trace 路径仍读取这些字段。

因此准确结论是：

```text
目标模型中可以删除；
当前代码中不能只删除 struct 字段和初始化语句；
必须先删除或改写所有语义消费者，再删除字段。
```

否则会导致内核编译失败；若只固定填 0 而保留消费者，则还会让依赖分类的路径静默失效。

## 5. 迁移执行参数不能误删

必须区分两种 `flags`：

```text
uvm_phase_f_region_t::flags
  旧 Region 业务分类字段，最终删除。

UVM_EXPERT_OFFLOAD_RELEASE_PARAMS::flags
  单次 release 的执行选项，必须保留。
```

例如 `SUBCHUNK_64K`、`REMOTE_READ` 决定一次 release 如何执行，不是在描述 Region 属于哪个业务对象。删除 Region 语义不能影响这些命令参数。

## 6. ABI 收敛方案

Phase-F register ABI 已是最小输入，不需要再传 `pool/layer/expert/role/flags`。旧 Phase-N query ABI 仍暴露语义字段，不能只改单侧结构体。

建议分两步发布：

### 第一步：兼容迁移

```text
1. 所有 Expert 控制改为应用层 explicit region-id list。
2. 删除内核自动 victim、pool budget/reclaim、role-based warm-prefetch/reserved 路径。
3. 旧 query ABI 暂时保持布局，已废弃字段固定返回 0。
4. C/C++ shim 与 Python 不再读取这些字段。
5. 用仓库全局搜索确认内核不再读取旧字段。
```

### 第二步：物理删除

```text
1. 删除 uvm_phase_f_region_t 旧字段及初始化。
2. 删除旧枚举、语义 flags 和只为它们存在的统计。
3. 同步修改 query ioctl、C/C++ shim 和 Python ctypes/解析代码。
4. query 最小输出只保留 region_id/base/length/state/found_by_va/rmStatus。
```

如果不需要 query-by-VA，则第二步还可直接删除该 ABI，而不是保留 `found_by_va`。

## 7. 验收条件

```text
内核可仅凭 region_id 找到 base/length 并完成 release/restore
内核不读取 pool/layer_id/expert_id/role/Region flags
应用层不等待内核选择 Expert 或 victim
重复 release/restore 由 state 幂等处理
UNKNOWN 状态不会被误当成 GPU 或 CPU
remote-read 与 64 KiB subchunk 执行参数仍正常
旧 ABI 兼容阶段不会发生结构体尺寸错位
最终内核、C/C++ shim、Python ABI 定义一致
```

# 三、必须修改：Hot Expert 初始化驻留保证

## 1. 当前缺陷

当前 `run_uvm_init_weight_offload()` 会编译全部 ExpertRecord，然后只对 cold Expert 执行 release。入口见 [run_uvm_init_weight_offload](D:/github/uvm/workloads/vllm/vllm/vllm/model_executor/layers/fused_moe/layer.py:2656)。

对没有被选为 cold 的 Hot Expert，当前逻辑隐含了下面的假设：

```text
没有主动 release
  == Expert 页面仍完整驻留 GPU
```

这个假设不成立。权重使用 UVM allocation 时，在 KV cache 分配、模型 warmup 或其他 HBM 压力之后，Hot Expert 的部分页可能已经迁移到 CPU。应用层或 Region 表中记录的 `state=GPU` 也不能证明此刻所有物理页实际驻留在 GPU。

当前后果是：

```text
初始化完成时 Hot Expert 看起来是 GPU 状态；
第一次正式请求命中该 Expert 时才触发 UVM fault；
fault 延迟进入首请求关键路径。
```

Cold Expert 不存在同样的不确定性：自定义 release 会把目标范围显式收敛到 CPU；remote-read 模式还会建立相应的 CPU backing/GPU read mapping。缺口集中在 Hot Expert 的初始化 GPU placement。

## 2. 修改目标

初始化完成前必须建立下面的保证：

```text
所有 cold Expert：已经完成 CPU release/remote-read setup
所有 hot Expert：全部 envelope VA range 已显式 prefetch 到 GPU
同步点完成后：才允许 worker 接收正式请求
```

这里不要求内核理解“Hot Expert”语义。Hot 集合仍由应用层计算，内核或 CUDA/UVM executor 只接收 VA range 或 Region ID 并执行搬运。

## 3. 正确的初始化顺序

推荐统一采用 post-warmup placement，避免 KV 分配或 warmup 再次改变刚建立的驻留结果：

```text
1. 完成模型加载、KV allocation 和 compile/warmup
2. 完成 KV dynamic target 的物理收敛
3. 编译并注册全部 ExpertRecord/envelope
4. 应用层确定 cold Expert 集合
5. 先 release 全部 cold Expert
6. 根据 all_local_experts - cold_experts 得到 hot Expert 集合
7. 汇总 hot Expert 的全部 envelope VA ranges
8. batch prefetch hot ranges 到 GPU
9. CUDA synchronize
10. 全部成功后提交 Hot Expert 的 GPU 状态
11. 允许 worker 进入 serving
```

必须“先 cold release，再 hot prefetch”。这样 cold release 先腾出 HBM，Hot placement 才在最终 KV/cold 布局上收敛，减少刚 prefetch 的 Hot 页被立即挤出的风险。

当前 post-warmup 入口位于 [_run_uvm_post_warmup_rebalance](D:/github/uvm/workloads/vllm/vllm/vllm/v1/worker/gpu_worker.py:769)，其后调用 [run_uvm_init_time_weight_placement](D:/github/uvm/workloads/vllm/vllm/vllm/v1/worker/gpu_model_runner.py:6329)。应在这一 placement 过程中加入 Hot placement，或紧随其后增加专用步骤；不要只在 `pre_kv` 分支 prefetch Hot Expert。

## 4. 建议新增的应用层流程

在 `run_uvm_init_time_weight_placement()` 中将“只 release cold”改为“完成最终双向 placement”：

```python
def run_uvm_init_time_weight_placement(self) -> None:
    records = compile_and_register_all_experts()
    cold_keys = select_cold_experts(records)

    release_cold_experts(cold_keys)

    hot_keys = all_expert_keys(records) - cold_keys
    hot_ranges = collect_envelope_ranges(hot_keys)
    outcome = batch_prefetch_ranges_to_device_with_executor(
        hot_ranges,
        device=torch.cuda.current_device(),
    )
    torch.cuda.synchronize()

    if not outcome.all_succeeded:
        mark_hot_experts_unknown(hot_keys)
        raise RuntimeError("Hot Expert GPU placement failed")

    mark_hot_experts_gpu(hot_keys)
```

可复用的底层入口是 [batch_prefetch_ranges_to_device_with_executor](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:1887)。

实现时不应按 Expert 逐个同步。应先合并相邻且不重叠的 envelope ranges，批量提交，最后只做一次必要的同步。

## 5. 状态提交规则

Hot Expert 不能在注册时无条件标记为 `GPU`。建议规则为：

```text
注册完成、尚未执行 placement：UNKNOWN
prefetch 已提交但未同步：PREFETCHING_GPU
全部 envelope prefetch 成功且同步完成：GPU
零成功或部分成功：UNKNOWN，并阻止进入 serving
```

如果一个 Expert 包含多个 envelope，只有所有 envelope 均完成 GPU placement，Expert 聚合状态才能为 `GPU`。不能用“至少一个 range 成功”代表整个 Expert 成功。

对内核 Region state 也采用同样原则：它只表示最近一次显式操作结果。即使应用层最终不需要逐 envelope 保存业务 metadata，内核仍要为每个 Region 保存自身 `state`。

## 6. 可选的严格驻留验证

启动阶段可在同步后调用 [driver_batch_query_ranges_residency_bytes](D:/github/uvm/workloads/vllm/vllm/vllm/device_allocator/uvm.py:1615)，验证：

```text
resident_gpu_bytes == queried_bytes
resident_cpu_bytes == 0
resident_unknown_bytes == 0
```

该查询仅作为启动正确性检查，不应形成新的常驻调试 metadata，也不应重新引入 `pool/layer/expert/role`。若查询开销较大，可受严格启动校验开关控制；正式状态提交仍必须依赖 prefetch 批次返回值和同步结果，而不能依赖日志。

## 7. 容量约束

prefetch 能保证初始化同步点的 placement，但不能把页面永久 pin 在 GPU。运行中若实际工作集超过 HBM，UVM 仍可能再次迁移页面。

初始化前必须检查或保守配置：

```text
Hot Expert bytes
+ KV target bytes
+ 非 Expert 模型权重
+ CUDA graph / workspace / scratch headroom
<= 可用 HBM budget
```

容量不足时应减少 Hot Expert 数或 KV target，不能依靠把状态字段写成 `GPU` 来掩盖超配。

## 8. 验收条件

```text
KV 分配和 warmup 完成后才执行最终 Hot placement
cold release 在 hot prefetch 之前完成
Hot Expert 的每个 envelope 都进入批量 prefetch
同步成功前 Hot Expert 不得标记 GPU
任一 envelope 失败时 Expert 标 UNKNOWN 并 fail-fast
严格模式下 Hot range 的 resident_gpu_bytes 等于 queried_bytes
首个正式请求命中 Hot Expert 时不产生由初始化缺页造成的 CPU->GPU fault
不为 Hot envelope 重新增加 pool/layer/expert/role 语义 metadata
```

# 四、统一实施顺序

建议按以下顺序修改，避免调试清理掩盖正确性问题：

1. 先修复 KV 迁移结果契约，使 `made_progress` 与 debug 开关无关。
2. 修复 KV 部分迁移的 quarantine、UNKNOWN 状态和回滚规则。
3. 增加 post-warmup Hot Expert 批量 GPU placement 与同步检查。
4. 删除 `_ensure_dynamic_pool_applied()` 的统计、snapshot 和嵌套 debug 返回值。
5. 将 Expert 策略彻底收敛到应用层的 `Expert -> envelope_region_ids`。
6. 删除内核 role/pool-based reserved、fault 分类、budget/reclaim 和自动 victim 路径。
7. 先停止 C/C++/Python 消费旧 query 字段，再删除内核旧字段。
8. 同步收敛 ABI、测试和文档。

最终应形成两个互不混淆的数据面：

```text
Expert：
  应用层选择 Expert 和 envelope IDs
  内核按 region_id 执行 release/restore
  内核 Region 仅保留 id/address/length/state

KV：
  应用层按 block 维护 scheduler 生命周期
  应用层按 PhysicalKVSpan 计算 VA range
  CUDA/UVM prefetch 按 VA range 执行物理迁移
  不依赖内核 Region 语义分类
```

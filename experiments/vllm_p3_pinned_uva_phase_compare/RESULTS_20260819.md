# 同步 P3、vLLM pinned 与自定义 managed-UVA 的阶段性能对比

日期：2026-08-19
正式结果：[`verification.json`](artifacts/20260819T_sync_p3_phase_formal_locked_v1/verification.json)（`status=pass`）

## 结论

当前同步 P3 已经是 eager、单卡、单进程范围内可完整运行的方案：注册计划、双 bank、512 KiB region、64 KiB PTE、copy/metadata 并行、CUDA compute/completion fence、O(1) bank commit、epoch 校验、失败封闭与安全销毁均在真实 vLLM 中通过。

性能结论则很明确：

- 1217-token、batch 4 的大 prefill 中，vLLM pinned 最快；P3 比 pinned 慢 `30.075 ms`（`38.2%`），但比自定义 managed-UVA 快 `12.768 ms`（`10.5%`）。
- 314-token、batch 1 的较小 prefill 中，managed-UVA 最快。此时按路由需求远程读取比固定搬完 2.25 GiB 更合适。
- decode 中 managed-UVA 最快，pinned 慢 `4.5%–7.2%`，P3 则约为另外两种机制的两倍。当前 P3 每个 token step 都重新搬运四层完整的 2.25 GiB，因此不适合持续用于 decode。
- 若不要求 fixed-VA，当前数据支持“大 prefill 用 pinned、decode 用 managed-UVA”。若必须保留 fixed-VA，P3 在大 prefill 中仍优于 managed-UVA，但应在进入 decode 后切换到远程访问；本次正式实验比较了三个独立机制，未把 P3→managed-UVA 混合切换计入同一条性能曲线。

## 公平性与测量契约

三个机制使用同一模型和同一权重地址选择：

- 模型：`Qwen3-30B-A3B-FP8`；单张 RTX 5090，tensor parallel size 为 1，eager 模式。
- 选择 L0–L3 的全部 128 个 packed experts，仅含 `w13_weight` 和 `w2_weight`。
- 每层 `576 MiB`，四层共 `2.25 GiB`；每层 1152 个 512 KiB region。
- P3 和 pinned 在每次 forward 都搬运全部选定字节。
- managed-UVA 映射相同的 2.25 GiB 范围，但实际 PCIe 读取由路由命中决定。因此这是相同模型/地址覆盖下的端到端机制比较，不是相同实际 PCIe 字节数下的纯带宽比较。

三个机制分别为：

- `P`：同步 fenced cmd96 P3；registered 512 KiB plan、64 KiB PTE、双 bank、copy-run/metadata cache、shared copy push、CUDA fence、bank-level O(1) commit、O(1) epoch validation 与 compact trace。
- `C`：vLLM exact-name pinned-host `copy_`，`non_blocking=True`，不额外加入逐层 host synchronize。
- `U`：项目自定义的 managed-UVA `remote_read`，覆盖同一组 expert regions。

阶段负载与统计方法：

- batch 1：314 个 prompt tokens；batch 4：1217 个 prompt tokens。
- 每进程、每 batch 先执行 1 次 conditioning，再执行 3 次正式测量。
- 每个 cycle 含 1 个严格 prefill step、5 个不计入 decode 主指标的 warmup decode steps，以及 16 个正式 decode steps。
- 每个 decode step 对每个请求恰好调度 1 个 token。
- 每个 engine step 前后均执行 `torch.cuda.synchronize()`；结果是 ready-to-use GPU wall time，不是异步 host-submit 时间。
- 每个机制运行 3 个独立进程，正式统计样本是每个进程内部中位数；表中再取 3 个独立进程中位数。
- 进程顺序为平衡序列 `PCU / CUP / UPC`，第二组进程反向扫描 batch 顺序。
- 运行时外部锁频目标为 SM `2400 MHz`、显存 `14001 MHz`；hot loop 内没有 NVML 查询、子进程、trace 检查或结果写盘。artifact 记录了 P0 和 `14001 MHz` 显存时钟，但没有保存外部锁频命令，因此锁频目标属于运行环境记录，而不是 verifier 可独立重建的证据。

完整运行配置见 [`run_config.json`](artifacts/20260819T_sync_p3_phase_formal_locked_v1/run_config.json)。

## 为什么三个阶段的排序不同

### 小 prefill

batch 1 只有 314 个 prompt tokens。P3 和 pinned 无论实际路由命中了多少专家，都搬完四层的全部 2.25 GiB；managed-UVA 只远程读取实际命中的 cache lines。因此 managed-UVA 以 `59.941 ms` 胜出，pinned 次之，P3 还要承担 fixed-VA 的 PTE/TLB、tracker、owner/generation commit 与 fence 开销。

### 大 prefill

batch 4 有 1217 个 prompt tokens，专家权重的复用明显增加。managed-UVA 的远程读取压力随 token 和路由命中增长，而 pinned/P3 的全量 copy 成本基本固定，因此排序变为 pinned、P3、managed-UVA。P3 的 CE copy 已接近正常搬运路径，但 fixed-VA cutover 和同步 ioctl 对控制线程的串行化使其仍比 pinned 多 `30.075 ms`。

### Decode

每个 decode step 只有每请求 1 个新 token。此时完整复制 2.25 GiB 的收益很低：

- 每个 P3 进程的 704 次 transition，其 ioctl 中位数分别为 `13.5901 ms`、`13.5638 ms`、`13.5544 ms`；进程中位数为 `13.5638 ms/层`。
- 每个 forward 执行四次 layer transition，四个同步 P3 ioctl 的墙钟时间合计约为 `54.255 ms`。
- 实测 decode step 为约 `110.5 ms`。数值上可拆为约 `54.3 ms` ioctl critical sections 和约 `56 ms` 其余执行，但这不是严格的 GPU 时间归因：ioctl 内的 compute-fence wait 可能包含前序 stream 工作。可以确定的是，四个同步 transition 均位于每个 token step 的关键路径，并破坏了 pinned 路径可以保留的 host enqueue-ahead。

因此 P3 decode 的问题不是 copy-run cache 失效，而是执行策略仍要求每 token 全层重搬。继续微调 sub-millisecond 校验无法改变这一数量级；需要在 decode 切换到 managed-UVA，或建立只覆盖实际 decode 路由需求的稀疏计划。

## P3 完整性证据

每个 P3 进程的理论 transition 数为：

```text
2 batches × 4 cycles × (1 prefill + 5 warmup decode + 16 measured decode)
          × 4 selected layers
= 704 transitions
```

三个 P3 进程均精确完成 704 次，共 2112 次：

- 2112/2112 使用 synchronous fenced cmd96 registered-plan executor。
- 2112/2112 compute fence 被接受、completion 被 signal、主 CUDA stream wait 被入队。
- 2112/2112 使用一个 shared copy push，registered plan、copy cache 和 target recipe 全部命中。
- clear recipe 为每进程 702/704、总计 2106/2112；每进程最初两次命中空 bank，不需要旧 owner clear。
- 2112/2112 使用 bank-level commit，`userspace_commit_slots=0`，没有回退到逐 slot 用户态提交。
- 0 fallback、0 error、0 conflict、0 poisoned session。

输出正确性也一致。三种机制在同一 batch 的 output token IDs SHA-256 完全相同：

- batch 1：`83dd1cdf2e151863a154ba5ee4cd1dab1b0db5e02ac0e1cd6c97c5a0c7eb7cbf`
- batch 4：`659c552b293f3060934ae3c63414bc4c7d75717617cb89d348f9117e5f9783e0`

销毁路径按 fail-safe 生命周期契约执行。每个 P3 进程注册 5 个 plans，4 个可安全显式销毁；当前 resident plan 保留至 session abort。最终 abort 成功释放 2304 个 slots、`1,207,959,552` bytes，剩余 slot 为 0。这里的 1.125 GiB 是两份 576 MiB bank，而不是四层各自常驻一份 bank。

正式运行前 phase harness 静态测试为 6/6 通过，9 个正式进程 return code 均为 0，运行时 verifier 最终为 `status=pass`。

## 初始化成本

`load_seconds` 测量从构造 vLLM `LLM` 到第一次 `torch.cuda.synchronize()` 完成，包含模型装载及相应机制的 offload/placement 初始化；它不在上述 prefill/decode 热路径延迟中：

| 机制 | 三进程 load 中位数 |
|---|---:|
| P3 | 95.648 s |
| pinned | 17.056 s |
| managed-UVA | 96.196 s |

P3 compact trace 还给出了其 plan/bank 子阶段的三进程中位数：

| P3 初始化子阶段 | 中位数 |
|---|---:|
| 第一 bank 预分配 | 141.402 ms |
| 第二 bank 预分配 | 136.447 ms |
| 注册 layer plans | 152.063 ms |
| 三项合计（逐进程求和后取中位数） | 428.284 ms |

其中内核 PTE prewarm 与 copy-cache build 合计中位数为 `73.082 ms`。

因此约 95 秒的 P3/managed-UVA load 值不能全部归因于 P3 plan 注册；它主要反映整条自定义 offload/placement 模型初始化路径。正式服务若频繁重启，需要单独优化或摊销该阶段。

## 限制与适用边界

- 本结果仅覆盖 eager、单 GPU、单进程；CUDA Graph 仍 fail-closed 拒绝，未验证 multi-GPU、NCCL 或通信流。
- 比较使用完整 packed 128-expert tensors，因为当前 vLLM pinned 参数 offloader 不能公平选择 packed tensor 内的 12 个专家切片；本结果不能直接外推到 sparse-12 copy。
- managed-UVA 的映射字节数与另两者相同，但没有在本实验中测量实际 PCIe demand-read 字节数。
- 每机制只有 3 个独立进程中位数。平衡顺序与外部锁频显著减少了升频偏差，但这仍不是大样本生产尾延迟研究。
- 相对差应优先参考三组 `PCU/CUP/UPC` 的 block-paired 结果；它们与表中边际中位数排序一致，但样本量仍只有 3 组。
- compact trace 的生产开销包含在 P3 数字中；benchmark 自身没有在 hot loop 内做文件 I/O。
- 当前 P3 decode 测的是“每步完整重搬四层”的保守实现，不代表未来稀疏 per-token plan 的上限。
- P3→managed-UVA 的阶段切换需要单独的正式 E2E qualification；本 artifact 只验证三个 process-isolated arms，不能把独立结果冒充为混合方案实测。

## 最终建议

同步 P3 已经满足“真实 vLLM 中可正确运行且可安全回收”的完成标准，但它不是三个机制中的通用性能最优解：

- 大 prefill：优先 vLLM pinned；必须 fixed-VA 时可使用 P3，并且 P3 明显优于 managed-UVA。
- 小 prefill：managed-UVA 更合适，避免无条件搬完整选区。
- Decode：优先 managed-UVA；不要让当前 full-layer P3 持续执行到每个 token step。

部署层面最值得继续验证的是“prefill 使用 pinned 或 P3，decode 原子切换到自定义 managed-UVA”的混合策略，而不是继续削减 P3 execute 中已经较小的校验开销。
